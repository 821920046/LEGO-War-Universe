删掉静默兜底，让输入真的决定输出

前十三轮我一直在自己造场景测重复。这一轮用户直接给了截图 —— 三句话，三处都指对了。

「换了两次内容了，每次第一个脚本的内容都是『两架战术直升机在灰尘弥漫的 城市街道低空悬停，四根粗索降绳掷下，特战队员呈战术姿态顺绳滑降，周围街道楼顶人影攒动。』 这到底是什么意思，没有使用AI吗」

那句话确实不是 AI 生成的 —— 它是《黑鹰坠落》第 1 镜的手写复刻文本 （CINEMA_DATABASE）。而 transpileMovieToLego 的结尾写着：
else { match = CINEMA_DATABASE.find(m => m.id === 'black-hawk-down') } // 通用硬派军事兜底
于是任何没命中库里 9 部影片的输入，都被静默替换成《黑鹰坠落》。 用 git HEAD 的旧版本实测 12 条任意输入，10 条拿到同一句直升机开场。
更关键的是触发条件：callAiBrain 先请求 /api/ai-brain，失败才走本地 —— 纯静态离线打开、或没配云端 Key 时，这条兜底就是主路径。 用户看到的不是「边缘情况」，是「默认行为」。

② 修法：把「匹配」与「兜底」拆开

修前 · cinema-homage.js

修后 · cinema-homage.js
export function matchCuratedFilm(query) {
  // 只回答「有没有命中」。两个方向分开看：
  //   · title.includes(q) —— 用户只打了片名的一部分（「黑鹰」→《黑鹰坠落》）
  //   · q.includes(alias) —— 用户在一句话里点名了这部片（「二战诺曼底登陆」→ 含『诺曼底』）
  // 删掉了反向的 alias.includes(q)：它让『战』『无人机』这类泛词也能命中。
  …
  return { film: null, kind: 'none' };   // 没命中就如实说没命中
}

export function transpileMovieToLego(query, requestedShots = 4, registry = null, { genericFallback = false } = {}) {
  const hit = matchCuratedFilm(query);
  const match = hit.film || (genericFallback ? CINEMA_DATABASE.find(m => m.id === 'black-hawk-down') : null);
  if (!match) {
    return { error: 'NO_CURATED_MATCH', matchedMovie: null, matchKind: 'none', shots: [] };
  }

genericFallback 的默认值从 true 翻成 false， 是这轮最有价值的一行改动。它把「静默兜底」从默认行为改成显式 opt-in —— 想兜底的调用方必须写 { genericFallback: true }，这个动作本身就是一次自我声明： 「我知道我在要一个通用军事兜底」。默认值决定了错误有多容易被犯。

命中与生成分成两条路，且各自如实标注

输入 → matchCuratedFilm() → 命中 → 策展复刻
策展致敬库 · 离线复刻（手写分镜，非 AI 生成）
输入 → matchCuratedFilm() → 未命中 → generateLocally()
本地自主想象引擎 · 离线生成（非云端 AI）

新增 local-engine.js 让前端与后台共用同一个 generateLocally() —— 此前后台 worker 只能去 import 前端客户端（ai-brain.js），这是说不通的， 也正是后台那条路没被覆盖到、静默退化的原因。

③ 修完之后，同一个 bug 换了张脸又出现了

删掉兜底之后，我以为问题解决了。实测 40 个题材， 26 个（65%）的首镜仍然是同一句 —— 只是从「同一部片」变成了「同一句话」：

根因在 TEXTURE.character：8 条节拍里 5 条是照片母题， 而域匹配只认 naval / air / orbital —— 陆战与指挥题材永远落到那 2 条通用条目，而它们两条都是照片。

这是同一个 bug 的第二个实例：不是「兜底到某一部片」，而是「兜底到某一句话」。

修法：池子重铺 + 确定性洗牌

组条数内容
通用6压弹匣 / 擦面罩 / 让水壶 / 摸照片（只留 1 条） / 插回胸挂 / 打手势

strategic2手指悬在确认键上 / 递一副耳机
naval air orbital各 2保留原有域专属节拍，各自补一条非照片的

排列数才是真正的瓶颈。原先的 rotate 是「整体轮转 k 位」—— 只有 arr.length 种排列。实测 10 个题材里有 4 个的开场撞成同一句 （都是「把头盔摘下来擦掉面罩上的灰」）。换成种子驱动的确定性洗牌后有 len! 种排列。

顺带发现 planFilm 把自己的 seed（含方案加盐）算好之后 没有传给 buildStory —— 后者自己重算了一个不含加盐的。 结果同一题材的 4 个方案共用同一套节拍顺序，「4 个不同方案」的开场仍然可能是同一句。

④ 最危险的那个：度量本身是坏的

上面「修前」那 5 行里，P袋里摸出 / P胸袋里摸出 / P从胸袋里摸出 看起来是 3 个不同骨架。它们其实是同一句话。

同一个节拍，只换人名 → 算出 3 个不同骨架
【TANGO】米勒从胸袋里摸出一张被汗浸皱的照片…      → P袋里摸出…
【VECTOR】邓肯从胸袋里摸出一张被汗浸皱的照片…     → P袋里摸出…
【LANTERN】伊万诺夫从胸袋里摸出一张被汗浸皱的照片… → P从胸袋里摸出…
【OVERSEER】施密特从胸袋里摸出一张被汗浸皱的照片…  → P胸袋里摸出…

正则 /【[^】]*】[\u4e00-\u9fa5]{2,4}/ 的贪心量词按「后面还有多少汉字」吃 2–4 字：
「米勒」+「从胸」吃 4 字；「伊万诺夫」只能吃 4 字（人名本身就是 4 字）；
「施密特」+「从」吃 4 字 —— 人名长度不同，切点就不同。

这意味着 6.8.0 那句「重合率降到 13–50%」是建立在一个低估重复的度量上的。 这不是产品 bug，是度量 bug；而度量 bug 比产品 bug 更危险 —— 它会让你相信一个不存在的改善。
6.7.6 的教训是「探针与实现同源就无法证伪自身」（两边共用同一套粗糙正则）。 这次的变体是「探针的正则自己就不稳」。两次的共性： 度量模块必须比被测对象更保守、更可验证，不能顺手复用一套凑合的正则。

遗留风险（如实记录）：

  • 跨题材开场重复只是从 65% 压到 5%，没有根除。上限由池子大小决定 （通用 6 条 / 每域 2 条）。继续压只能继续铺内容 —— 这不是算法问题， 是「一个 6 条的池子里，最常用的那条必然占 1/6」。
  • 同题材 4 方案的开场是 2–3 种而非 4 种：4 个方案铺在 3 个「叙事重心」上， 按鸽笼原理必然有两个共用重心。要根治得让「重心」参与更多组合，而不是继续调排列。
  • domainOfText 对古代 / 历史题材有空白（城堡 草原 骑兵 沙漠风暴 都判不出域）， 这些题材只能落到通用池。补域规则会同时影响环境与演员选型，本轮没动。
  • 策展库仍只有 9 部，且现在只有「真的点名影片」才命中。 想让更多经典片走复刻路线，是内容工作量。
  • 边界仍然没有变：这些 prompt 依旧一次也没有跑过 Veo 3 / Flow。 第十四轮推倒的是一堵我自己的墙，不是「自洽 ↔ 有效」那堵。
