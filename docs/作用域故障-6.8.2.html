LEGO War Universe · 6.8.2 · Acceptance

「renderVariantPicker is not defined」：三个函数被缩进骗了

报错说它未定义，可它明明写在模块顶层 —— 这个矛盾本身就是线索。

✕ 转译失败: renderVariantPicker is not defined
转译异常: renderVariantPicker is not defined

▲ ReferenceError: renderVariantPicker is not defined
    at renderCurrentProject (app.js:1353:5)
    at boot (app.js:242:2)

顶格的 function 声明会被提升到作用域顶端 —— 它不可能 "not defined"。 所以只剩一种解释：它看着在顶层，实际不在。
6.8.0 新增这三个函数时，我把它们插在了 $('plan').onclick = … 之后， 而那行位于 bindGlobalEvents() 体内（第 787 行开、第 1265 行才闭合）—— 三个函数被无声地吞成了 bindGlobalEvents 的局部函数。

一、定位方法：不要数括号，让 V8 自己回答

第一反应是数括号。我写了个括号深度扫描器，它说文件末尾深度是 1、这两个函数都在深度 1 —— 但这和运行时矛盾：如果 renderCurrentProject 在深度 1，boot()（深度 0）就调不到它， 而栈里明明写着 at boot → at renderCurrentProject。 我的扫描器不认正则字面量（这个文件里满是 replace(/…/g, …)），它不可信。

换成不依赖我自己写的任何解析逻辑的判据：给每个顶格函数追加一句 export { 名字 } 再交给 V8 解析 —— 只有真正的模块顶层绑定才能被导出。

二、真实结构：一个根因，两个症状

src/ui/app.js · 修复前

注意 bindGlobalEvents 自己调用它们是好的（第 1053/1054 行就在同一个作用域里）—— 这个 bug 只在「从外层调用」时才暴露。而模块顶层恰好有两处外层调用：

症状 A · 页面加载后镜头列表整块空白

boot()→ 第 242 行 renderCurrentProject()→ 第 1353 行 renderVariantPicker()→ ReferenceError，boot 中断

症状 B · 点「深度转译」弹「转译失败」

executeMovieTranspile()→ 第 754 行 renderVariantPicker()→ 抛错 → 被 catch 成「转译异常」

它为什么藏了这么久？ renderCurrentProject 里那处调用外面有守卫： if (!currentProject.variant || variant 过期) { renderVariantPicker(); } —— 生成过一次之后页面是好的（variant 刚写进去、标签也对得上），刷新或打开旧工程才炸。 所以 6.8.0 上线时自测「看着没问题」。

时间线：6.8.0 引入 → 6.8.1 加重 → 6.8.2 才修。 用同一判据复核 a5eb8d9（6.8.0），三个函数同样不是顶层； 而 6.8.1 又在 executeMovieTranspile 里加了一处无条件调用（第 754 行）， 把「偶尔炸」变成「每次都炸」—— 这一轮才会被撞上。

三、为什么五道门禁全绿却一条都没拦住

门禁为什么放过它
syntax.test.mjs（解析每个模块） 函数写在顶层还是写在别的函数里，都是合法语法
288 条单测 全部只覆盖 src/domain/**，纯函数、不碰 DOM
validate.py / build-assets 只关心资产 JSON
check-release.mjs 只关心发布面（版本号、签名、文件齐全）
run-blind-test.mjs 只走 domain 层编译链，从不加载 app.js

app.js 在 Node 里 import 不进来（要 DOM），所以它从来没有被真正执行过一次。 最讽刺的是 tests/syntax.test.mjs 的注释里早就写着这句话： 「……让整个页面白屏，而全部单测绿灯、发布门禁也通过 —— 测试通过 ≠ 页面能跑」。 写这段注释的时候，我以为「解析一遍」就等于「页面能跑」。 它只做到了「解析」，没做到「运行」—— 而这两者之间的缝，正好装得下这个 bug。

四、修法

① 纯搬移

三个函数从 bindGlobalEvents() 体内移到它结束之后。 逐行比对行内容多重集：完全一致，行数 1404 → 1404 —— 机械证明没丢代码。

② 静态作用域门禁

tests/syntax.test.mjs 新增：每个顶格函数声明都必须是真正的模块顶层绑定。 能定位到名字。

③ 动态启动冒烟

tests/ui-boot.test.mjs（新增）：最小 DOM 桩真的把 app.js 跑起来。 能抓到静态看不出的运行期问题。

④ 顺手修掉悬空脚本

test:smoke 原本指向不存在的 tests/smoke.mjs —— 一个指向空气的脚本不会报错、也没人发现。

七、遗留风险（如实记录）

· 启动冒烟只覆盖「加载 + 一次影院转译」。导出、抽屉、工程切换、自我进化面板、审核队列 这些交互路径仍然只有静态契约检查（id 存不存在），没有运行时覆盖。
· public/build-manifest.json 的 builtAt 是时间戳，每次 npm run build 都会让工作区变脏 —— 长期噪音，本轮没动。
· 边界仍然没有变：这些 prompt 依旧一次也没有跑过 Veo 3 / Flow。 本轮推倒的是第三堵我自己的墙 —— 前两堵是「输入不决定输出」（6.8.1）与「生成内容重复」（6.8.0）。 三堵墙都是自洽性问题，不是有效性问题。

八、元发现

6.8.1 我写下的教训是「测量维度的选择本身就是一种偏见」。这一轮的教训更具体：
门禁的覆盖面本身就是一种偏见。五道门禁全围着 src/domain/** 打转 —— 那是「好测的部分」。于是测试体系在整体上给人一种「都覆盖了」的错觉， 而用户真正会打开的那个文件，一行都没被执行过。
一个恒绿的门禁比没有门禁更危险：它提供的是虚假的安全感。

还有一层：用户两次投诉，两次都精准指向我没有测量的那一维 —— 第一次是「输入变了输出没变」（我从没测过跨题材差异）， 第二次是「页面直接报错」（我从没执行过页面）。 用户不是在给我挑错，他是在替我指出我的盲区。
