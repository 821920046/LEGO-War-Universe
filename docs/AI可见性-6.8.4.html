「AI 不是已经配了 api 了吗」：让失败可见

上一轮刚写完「怎么配置 AI」的权威文档，用户紧接着说：我配了，还是用不了。于是这次不再推理 —— 直接探测线上。

用户追问：「AI不是已经配了api了吗?还不能使用吗」

6.8.3 花了整整一轮把「怎么配置 AI」写成逐条对得上代码的文档。
按理说用户拿着它应该能自己解决 —— 但他没有。

这时候有两条路：① 继续读代码、继续猜他配错了哪里，再写一份更详细的文档； ② 直接测量 —— 线上到底有没有 Key？发一个请求就知道。
我选了第二条。整个过程不到 5 分钟，拿到了确定答案。
用户说的「我配了」和系统实际的状态，是需要分别测量的两件事。

latencyMs: 193 是决定性的。 一次外部 HTTPS 调用（DNS + TCP + TLS + 响应）最低也要上百毫秒；而 193ms 还要装下完整的本地生成。 这个数字说明：后台根本没有发起过任何网络请求 —— 一个 Key 都没配。

二、根因：三个「看不见」叠成一个信息黑洞

诊断出「没配 Key」之后，真正值得追的问题是：为什么用户配了之后，界面上看不出任何异常？

① 前端静默回退

callAiBrain 在接口失败时直接走本地引擎，不提示原因。用户看不到任何错误。

② 徽章无条件绿色

$('ai-brain-status').className = 'badge badge--ok' 是写死的，与是否真的用了 AI 完全无关。

③ 没有自检入口

provider 失败只写进 console.warn，用户永远看不到；?probe=1 返回 405 —— 连查都没得查。

三层叠起来，形成一个完美的信息黑洞：
配了 Key 没用上 → 界面看不出异常 → 只能来问「不是配了吗」。

这里有一个值得记下的转化 —— 错误一旦被静默吞掉，它就不再是错误，而变成了一个用户体验问题。 一个「配置没生效」的技术问题，被三层静默包装成了「功能正常」的假象。

三、修复前 vs 修复后：徽章长什么样

修复前 · 无论走没走 AI，都是这个绿色

🧠 本次引擎：本地自主想象引擎 · 离线生成（非云端 AI）

$('ai-brain-status').className = 'badge badge--ok';   // ← 写死的
// 文案写着「非云端 AI」，但颜色是成功的绿色 —— 用户扫一眼只会觉得「一切正常」

🧠 未使用云端 AI：本地自主想象引擎 · 离线生成（非云端 AI）（后台未配置任何模型 Key —— 见 /api/ai-brain?probe=1 自检）

const usedAi = result.isAiGenerated === true;
$('ai-brain-status').className = usedAi ? 'badge badge--ok' : 'badge badge--warn';
// 黄色 = 走的本地引擎，并直接写出原因（没配 Key / 云端调用失败 → groq Groq HTTP 401）

四、修法

层改动
后端 · 只读自检 新增 GET /api/ai-brain?probe=1：报告哪个 Key 配了、哪个没配。掩码只给后四位与长度（••••1234（长度 56）），不发起任何外部调用、不消耗额度、不返回密钥本身。不带 probe 的 GET 仍然 405（契约不放宽）
后端 · 诊断随响应回传 所有响应体新增 aiStatus：aiAvailable / reason（OK / NO_KEYS_CONFIGURED / ALL_PROVIDERS_FAILED）/ 每个 provider 的 configured / tried / error（真实 HTTP 状态码）/ hint
前端 · 徽章诚实 仅当 isAiGenerated === true 才是绿色；回退本地一律黄色并写出原因。策展面板那处无条件 badge--ok 同样修正
文档 docs/AI启用时机与配置.md 新增「零、5 秒自查」章节；README 部署章节补上此前完全缺失的 GROQ_API_KEY 一行

自检长什么样

GET /api/ai-brain?probe=1 —— 只读、零额度、不泄露密钥
{
  "aiAvailable": false,          // ← 一句话结论
  "configuredCount": 0,          // ← 配了几个 Key（0 = 一个都没配）
  "providers": [
    { "id": "groq",       "envVar": "GROQ_API_KEY",       "configured": false, "keyHint": null },
    { "id": "openrouter", "envVar": "OPENROUTER_API_KEY", "configured": false, "keyHint": null },
    { "id": "gemini",     "envVar": "GEMINI_API_KEY",     "configured": false, "keyHint": null }
  ],
  "diagnosis": "后台没有配置任何模型 Key……",
  "howToFix": ["Cloudflare 控制台 → ……", "……"]
}

设计取舍：自检只回答「配了没」，不主动验证 Key 是否有效 —— 因为验证有效性必须真的调用一次、会消耗额度。 而「配了但无效」这件事，点一次「深度转译」就能从 aiStatus.providers[].error 看到真实 HTTP 状态码： 用真实路径做体检，不额外花钱。

error 码对照表

error含义怎么办
Groq HTTP 401Key 无效或已被撤销重新生成一把 Key
Groq HTTP 429额度用尽 / 触发限流换一个 provider，或等额度重置
Groq HTTP 404模型名不可用检查 provider 的模型是否下线
NOT_CONFIGURED这个 provider 压根没配见 howToFix

六、一处自我更正

6.8.3 我写下的结论（错的）
「AI 路径依然没有任何自动化测试。」
6.8.4 更正后的事实
tests/backend-ai-brain.test.mjs 有 14 条测试，tests/imagination-681.test.mjs 也在测这个端点，
包含用 mock fetch 覆盖的 provider 成功 / 失败 / 内容治理分支。

代码写错了会被测试抓住，结论写错了不会。 一个错误的结论会安静地留在报告里，被后续每一轮当成事实引用。 所以这一轮我把它明写在 CHANGELOG 里，而不是悄悄改掉 —— 更正必须留痕，否则它就变成了另一种静默。

八、遗留风险（如实记录）

· 自检只回答「配了没」，不主动验证 Key 有效性（那需要真的调用、会消耗额度）。 「配了但无效」要靠点一次「深度转译」看 aiStatus.providers[].error。
· 06_Deploy/worker.js 仍只支持 gemini/openai，前端调不到它。
· public/build-manifest.json 的 builtAt 仍是时间戳，每次构建都让工作区变脏。
· 边界仍然没有变：这些 prompt 依旧一次也没有跑过 Veo 3 / Flow。 前四轮推倒的都是自洽性问题（生成重复 / 输入不决定输出 / 作用域嵌套 / 文档失真）， 这一轮是第五堵墙：可观测性。 五堵墙全部是「我的系统在骗我或骗用户」，没有一堵是「内容不够好」。

九、元发现

6.8.3 的教训是「文档是最没有门禁的那一层」。这一轮更进一层：

错误一旦被静默吞掉，它就不再是错误，而变成了一个用户体验问题。

后台把 provider 的失败写进 console.warn（用户看不到）， 前端把回退画成绿色（用户以为成功）， 自检接口根本不存在（用户无从查证）—— 三个「看不见」叠起来，把一个配置问题伪装成了功能正常。

这一轮还验证了一件前几轮反复出现、但这次终于说清楚的事：
用户说的「我配了」和系统实际的状态，是需要分别测量的两件事。 我没有去问用户「你配在哪了」，而是直接探测线上 —— 5 分钟拿到确定答案。
凡是能实测的，就不要靠提问去猜。
