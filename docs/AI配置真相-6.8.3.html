「什么时候该用 AI，还要怎么配置」：答案不该藏在代码里

一个知识性问题，暴露了整条流水线从未检查过的一类资产 —— 文档。

用户提问：「什么时候该用AI，还要怎么配置」

这不是一个 bug 报告。没有任何东西是红的：
五道门禁全绿、测试 291 全过、盲测 100 / 100 / 100 / 96。
可这个问题的答案，仓库里没有一处是对的。

代码有门禁，文档没有。语法错误会让 npm test 变红， 作用域错误会被启动冒烟抓到 —— 可 06_Deploy/README.md 可以连续几个月 描述一个不存在的系统，没有任何一条流水线会因此变红。

一、三份文档，三份都和代码对不上

文档它写的代码里的实情
06_Deploy/README.md AI 端点是 /api/compose；10 个 provider；支持 MODELS / ROTATE / TIMEOUT_MS；网页里有「启用 AI 增强」勾选框 全都不存在。真实 AI 端点是 /api/ai-brain，只有 3 个 provider，前端没有任何开关。grep "MODELS\|ROTATE\|TIMEOUT_MS" 全仓库 0 命中
.env.example 「本地开发时配置到 .env 中」 代码里没有任何 dotenv 加载（grep dotenv 为空），.env 根本不会被读取
README.md 本地部署用 python -m http.server 8080 那只提供静态文件、没有 Functions —— 本地这么起永远走本地引擎，配了 Key 也用不上

第三行最阴：它不是错，python -m http.server 确实能起一个网页。 但它起的是一个没有后端的网页 —— 页面能打开、能点「深度转译」、也能出分镜， 一切看起来都正常，只是永远走本地引擎。用户配了 Key、照着做了、功能"能用"， 于是没有任何理由怀疑自己配错了。这比直接报错更糟：一个静默的失败， 用户会以为自己成功了。

三、顺手挖出的一个密钥泄露面

6.8.3 之前的 .gitignore（节选）
.env
.env.local
.env.*.local
（……没有 .dev.vars）

.dev.vars 正是 Cloudflare 的本地环境变量约定文件 —— wrangler pages dev 官方文档明确要求你建它来放本地密钥。 也就是说：仓库主动邀请你创建一个会被提交上去的密钥文件。 这不是「文档没写」，是仓库配置本身在制造泄露。

6.8.3 之后
.env
.env.local
.env.*.local
# Cloudflare 的本地环境变量约定文件（wrangler pages dev / wrangler dev 会读它）。
# 6.8.3 之前**没有**忽略它 —— 按标准流程建 .dev.vars 填真 Key 会被 git 提交上去，
# 等于把 API Key 直接推到远端。凡是可能装密钥的文件都必须在这里列全。
.dev.vars
.dev.vars.*
.wrangler/

教训：.gitignore 的完备性，不能按「我知道哪些文件装密钥」来写， 要按「这套工具链会让人创建哪些装密钥的文件」来写。.dev.vars 就是后者的典型 —— 我不该"知道"它，我该推导出它：既然项目用 Cloudflare Pages、既然本地要用 wrangler， 那 wrangler 的密钥约定文件就必然会被创建。

四、一个孤儿目录

06_Deploy/ 在仓库里没有任何一处被引用：README.md 不提它、 docs/ 不提它、package.json 的脚本不指向它。而它的名字叫 06_Deploy（第六步：部署）—— 一个按命名看起来最该被信任的目录，恰恰是错的。

孤儿目录的危险不在"没人看"，而在"某天有人会看"。用户今天问的「怎么配置」， 就是那个"某天"。他打开这个目录，照着做，然后失败，然后困惑 —— 而我从没检查过它。

什么时候「该」用 AI —— 设计判断，不是配置项

✅ 该用

抽象 / 叙事型主题（「一个老兵在废墟里回忆战友」）· 风格迁移（「像《黑鹰坠落》那种感觉」）· 需要原创立意（logline / twist / hook）—— 这三类本地规则引擎天生做不好。

❌ 不该用

明确的历史战役 / 装备题材（本地有 810 项真实资产 + 时代门控，确定、毫秒级、免费）· 已点名 9 部策展影片（手写复刻本来就比模型稳）· 需要可复现（本地确定性，AI 带 temperature: 0.7）。

边界

AI 只负责「选资产 + 写动作句 + 声明戏剧功能」。最终 Prompt 仍由本地编译器按 Production Bible 组装 —— 风格块、negative、角色一致性描述不会被 AI 改写。

这条边界回答了「什么时候该用 AI」的深层问题：不是"AI 能不能做"， 而是"我允许 AI 做哪一段"。一旦想清楚交付物里哪部分必须确定，AI 的适用范围自然就划出来了。

七、遗留风险（如实记录）

· AI 路径依然没有任何自动化测试。/api/ai-brain 的 3 个 provider 分支、 限流、CORS、governResponse 都没有覆盖 —— 本轮只修了文档，没修这条空白。 而且要诚实：就算补上测试，也只能验证"路由对不对"，验证不了"模型产出的分镜好不好看"。
· 06_Deploy/worker.js 仍然只支持 gemini/openai，前端调不到它。 本轮只是把这一点如实写进文档，没有动代码 —— 因为动它属于新增能力，不属于回答"怎么配置"。
· public/build-manifest.json 的 builtAt 是时间戳，每次 npm run build 都让工作区变脏。本轮没动。
· 边界仍然没有变：这些 prompt 依旧一次也没有跑过 Veo 3 / Flow。 前三轮推倒的是「生成重复」（6.8.0）、「输入不决定输出」（6.8.1）、「作用域嵌套」（6.8.2）—— 全是自洽性问题。这一轮连自洽性都不涉及，纯粹是知识与文档的准确性问题。

八、元发现

前三轮的教训分别是：「测量维度的选择本身就是一种偏见」（6.8.1）、 「门禁的覆盖面本身就是一种偏见」（6.8.2）。

这一轮的教训是：文档是最没有门禁的那一层。 代码有语法门禁、作用域门禁、启动冒烟、盲测、发布检查五道防线。 而 06_Deploy/README.md 可以连续几个月描述一个不存在的系统， 没有任何一条流水线会因此变红。于是它腐烂得最彻底 —— 因为它连"被发现"的机会都没有。

更值得记的是这个 bug 的暴露方式：它不是被我测出来的，是用户问出来的。 用户问「怎么配置」，等于替我执行了一次「文档与代码一致性检查」—— 而我此前从未把这项检查写进任何流程。
凡是"人照着做会失败"的知识，都需要一条门禁；否则它一定会腐烂。

还有一层，和前两轮是同一个模式：
用户第一次投诉「输入变了输出没变」→ 我发现了"我从没测过跨题材差异"；
用户第二次投诉「页面报错」→ 我发现了"我从没执行过页面"；
用户第三次问「怎么配置」→ 我发现了"我从没核对过文档"。
三次都是用户替我发现盲区。而三次我都应该能自己发现 —— 只要我肯问自己一句：
"这段知识，如果有人照着做，会不会失败？如果会，我测过吗？"
