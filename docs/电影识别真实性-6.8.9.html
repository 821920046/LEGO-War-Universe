6.8.9 · 修复记录

治「为不存在的电影编造导演」——想象力留下，幻觉根除

LEGO War Universe · 2026-10-16 · 用户截图触发 → curl 复测两次稳定复现 → 三层修复 + 4 条门禁（全部反向验证）→ 线上复测 3/3 自编片名不再编造导演

"我要的是这个项目能够持久，要有想象力，才能把这些视频脚本写的更好。"—— 所以修法不是堵死想象力，而是分清素材与谎言。

〇、现象：一次用户截图

用户在影院模式输入自编片名，得到一份看起来完全正常的「解构结果」——问题全在细节里：

用户截图与两次 curl 复测（输入均非真实电影）
输入「热带雨林狙击手生死对决」
  → 《热带雨林狙击手生死对决》导演：丹尼斯·维伦纽瓦 · 2025（截图）
  → 同一输入复测：导演：丹尼斯·维伦纽瓦 · 2024   ← 连编的年份都不稳定

输入「赛博朋克熊猫特工队大电影」
  → 导演：诺兰、雷德利·斯科特、丹尼斯·维伦纽瓦 · 2077
    （模型自己给年份标了"(虚构)"，却照挂三位真实在世导演的真名）

三个事实：① 对不存在的片名，模型不报「查无此片」，而是配合演出现编全套元数据；② 作品被挂到真实在世导演名下（治理黑名单只拦政治人物，这条路径完全不在拦截面内）；③ UI 照常显示「乐高适配度高：已完成认证资产」，编造的结果看起来像一次成功的真实解构。

一、定性：这不是 bug 级失误，是稳定行为

根因在 system prompt：它只说「用户的输入可能是一部电影名称……你的任务是解构并转译」，没有任何一句告诉模型「不认识就必须承认」。训练有素的模型面对一个像片名的字符串，默认行为是配合演出——片名越像真的，它演得越认真。

危险在于它不可分辨：用户无法从界面区分「这是解构《狂怒》」和「这是现编的」。而「为不存在的电影挂真实导演名」是可以被截图外传的假消息。

二、修法：三层，想象力一分不少

① prompt：最高优先级零

「真实性与署名纪律」置于所有既有规则之前：只解构确切知道的真实电影；不认识必须输出 recognized:false 且四个元数据字段留空；director 只允许填**该真实影片的真实导演**；致敬只能写成「诺兰式实拍质感」这类风格化表述，绝不可作为署名。

② 处理层：如实记账 + 转原创

云端返回 recognized:false 时，这次成功如实记为 unrecognized，aiStatus.reason=UNRECOGNIZED_INPUT，result 置空落入本地原创引擎：用户自编的片名作为题材参与原创生成（输入不被浪费），engine / isAiGenerated 如实标注。

③ 门禁：4 条全绿 + 全反向

处理层转原创 / 正常路径不误伤 / 实际发出的 prompt 必须含规则（直接断言 prompt 文本）/ 静态防回归。反向验证：删后端处理→门禁 1 红；删 prompt 规则段→门禁 3/4 红。

可见性纪律：新 reason 有专属 hint（「防幻觉路径，非故障」）与前端徽章文案——否则用户会以为云端坏了；「未识别 → 已按题材原创」这句话本身就是「为什么没有导演和年份」的解释。

三、边界（不改的与原因）

对象处置原因
策展库 9 部手写影片的导演（科辛斯基、雷德利·斯科特…）不动真实影片的真实导演，事实陈述
本地原创引擎 director不动本来就是 null，本就干净
真实影片的解构（用户输入《狂怒》→ 真实导演）照常门禁 2 专门守「不误伤」
用户自编片名的原创生成增强片名作为题材喂给本地引擎，想象力保留

4.1 发布后线上复测（PR #26 承诺的诚实边界，已兑现）

6.8.9 部署上线（线上 projectVersion=6.8.9）后，对 https://lego-war-universe.pages.dev/api/ai-brain 实发请求。复测脚本的判据刻意区分「被测对象失败」与「检验过程失败」：网络抖动 / 非 JSON / 非 200 一律标为检验过程失败，不计入结论。

                                    isAiGenerated=true · director=大卫·阿耶 · reason=OK · 4 分镜

结论：三个自编片名全部按设计走「不识别 → 本地原创」，无一编造导演；真实影片未被误伤，仍走云端 AI 并给出真实导演。《狂怒》2014 年导演大卫·阿耶（David Ayer）为事实正确项。

样本量的诚实边界：这是 4 次成功调用，只能说「本次未复现」，不能说「幻觉已根除」。模型是否继续听话取决于上游模型本身，而候选模型会腐烂（gemini-1.5-flash、gemini-2.0-* 已退役）——门禁钉住的 prompt 规则与处理层不会随模型退役失效，但「模型是否服从」这一层只能靠持续线上复测维持。

  groq     llama-3.3-70b-versatile   ok=false  7ms    Groq HTTP 403    ← Key 仍被拒，需控制台重生（6.8.7 已知）
  gemini   gemini-2.5-flash          ok=false  27461ms Gemini HTTP 503
  gemini   gemini-3.5-flash-lite     ok=false  410ms   Gemini HTTP 503  ← 免费档过载（6.8.7 已知）
  gemini   gemini-3.8-flash          ok=false  12265ms Gemini HTTP 503
  → engine=本地自主想象引擎 · 离线生成（非云端 AI），但 reason 是 ALL_PROVIDERS_FAILED 而非 UNRECOGNIZED_INPUT

这一样本恰好第三次证明设计目标：「模型说不认识」与「模型根本没到/没回」在前端徽章与 aiStatus 上是两条不同的路。如果两条路被合并成同一个 engine 字符串，用户在 503 风暴下会看到和「防幻觉成功」完全一样的徽章——那正是 6.8.7 aiStatus 遥测要消灭的混淆。

复测附带确认的运维现状：线上 probe configuredCount=2（groq、gemini），openrouter.configured=false —— 6.8.7 中用户已填写的 OpenRouter Key 在运行时仍不可见。变量要么没保存到 Pages 项目级、要么保存后未触发重新部署。这不是代码问题，控制台侧的变量必须重新走一次「保存 → Redeploy」；groq 的 403 同理需要用户到 Groq 控制台重新生成 Key。

LEGO War Universe · 6.8.9 · 元教训：当系统开始「配合演出」，症状往往不在报错里而在成功里 —— 一次看起来很成功的解构，可以整个是编造的；判据不是「这次调用 ok 了吗」，而是「输出里的每个事实声明有来源吗」。线上复测 3/3 未复现后仍只写「本次未复现」而不写「已根除」—— 模型会腐烂，服从性无法被一次测试永久证毕。
