「我配了 Key」是对的，是我上一轮诊断错了

6.8.4 我刚上线只读自检，并据此宣布「后台一个 Key 都没配」。自检上线后的第一件事，就是推翻了我自己的这个结论。

6.8.4 我写下的推断：

「latencyMs: 193 是决定性的。一次外部 HTTPS 调用最低也要上百毫秒……
这个数字说明：后台根本没有发起过任何网络请求 —— 一个 Key 都没配。」

这个推断是错的。

403 / 404 这类快速失败的调用（DNS 已在边缘缓存、TLS 可能复用）完全可以在几十毫秒内返回。 两次快速失败 + 本地生成，193ms 是装得下的。
我犯的错很具体：用一个间接信号（延迟）去代替直接测量（自检），然后把它当成结论写进了报告。
而讽刺的是 —— 我为此专门建的自检接口，上线后第一件事就是证伪了它。

一、线上实测：用户说得对

GET /api/ai-brain?probe=1（自检上线后立刻探测生产环境）
{ "aiAvailable": true, "configuredCount": 2,
  "providers": [
    { "id": "groq",   "configured": true, "keyHint": "••••iSqX（长度 84）" },
    { "id": "gemini", "configured": true, "keyHint": "••••xvuU（长度 39）" }
  ] }

用户确实配了 Key —— 两个。再看 POST 的 aiStatus：

POST /api/ai-brain（真实生成请求）
{ "reason": "ALL_PROVIDERS_FAILED",
  "providers": [
    { "id": "groq",   "tried": true, "error": "Groq HTTP 403" },
    { "id": "gemini", "tried": true, "error": "Gemini HTTP 404" }
  ] }

两个 Key 都在，两个都失败了。这才是真问题 —— 而它在 6.8.4 之前完全不可见。 用户从第一轮就在说「我配了」，他是对的；错的是我的诊断。

二、两个失败，两个完全不同的根因

① Gemini HTTP 404 —— 模型名早已退役（代码 bug）

代码里硬编码 gemini-1.5-flash。Google 官方退役表里，1.5 系列连条目都没有，2.0 系列也已在 2026-06-01 关停。这条路已经静默 404 了很久。

② Groq HTTP 403 —— Key 被 Groq 拒绝（配置问题）

我用一把故意写错的 Key 直接打 Groq 接口复现，返回的正是 HTTP 403 {"error":{"message":"Forbidden"}} —— 与线上完全一致。这条代码侧修不了。

Google 官方退役表（查证结果）

模型状态

gemini-2.0-flash / gemini-2.0-flash-lite2026-06-01 已关停
gemini-3.8-flash / gemini-3.5-flash-lite当前可用（Google 官方推荐新项目使用）

    -H "Authorization: Bearer gsk_BOGUSKEYFORPROBE..." \
    -d '{"model":"llama-3.3-70b-versatile", ...}'

三、根子不是「写错了模型名」，而是「把模型名写死了」

模型名会腐烂。gemini-1.5-flash 当年是正确选择；它退役不是任何人的错。 真正的错误是把模型名硬编码进函数体 —— 一次退役就永久失效，除了改代码没有任何办法修，而且失效是静默的。

这构成一个永久性缺陷类别：
凡是「外部契约」被硬编码进代码的地方，都会在外部契约变化时静默失效。
模型名是外部契约，API 版本是外部契约，第三方字段名也是。

四、修法：让「模型腐烂」不再是一次性致命伤

改动说明
候选模型列表每个 provider 内置一串候选，逐个尝试；第一个 404 就自动换下一个。实测：gemini-3.8-flash 404 后自动切到 gemini-3.5-flash-lite 并成功
环境变量覆盖GROQ_MODEL / OPENROUTER_MODEL / GEMINI_MODEL（可逗号分隔多个）。换模型不用改代码
三个函数 → 一个通用函数callGroq / callOpenRouter / callGemini 合并为 callProviderModel(provider, model, …)，URL / 请求头 / 是否 json 模式全部数据化
advice 字段光有 Groq HTTP 403 用户仍不知道干什么。新增把状态码翻译成「人话 + 下一步」的映射
前端弹可操作提示仅在「配了 Key 但调用失败」时弹 toast（写明下一步）；没配 Key 是正常状态，不打扰
自检报告候选列表?probe=1 现在同时返回每个 provider 的 modelEnvVar 与 models
候选列表的核心价值：单个模型退役，整条路不会哑掉
尝试顺序 = ["gemini-3.8-flash", "gemini-3.5-flash-lite"]
gemini/gemini-3.8-flash 调度失败: Gemini HTTP 404
最终 model = gemini-3.5-flash-lite | ok = true
engine = Cloud Free AI (Gemini (gemini-3.5-flash-lite))
advice：把状态码翻译成「下一步怎么办」
Groq HTTP 403
→ Groq 拒绝了这把 Key（403 禁止访问）：常见原因是 Key 无效 / 已撤销 / 账户受限或未完成验证 /
  所在地区不支持。请到控制台确认 Key 状态，或换一把新 Key。

Gemini HTTP 404
→ Gemini 找不到模型「gemini-2.5-flash」（404）：多半是这个模型名已经退役。
  用环境变量 GEMINI_MODEL 指定一个当前可用的模型名即可，无需改代码。

七、遗留风险（如实记录）

· Groq 那把 Key 需要用户自己去控制台处理（403 是服务方拒绝，代码侧无法修复）。
· 候选列表里的模型名同样会腐烂 —— 只是现在腐烂的代价从「永久失效」降为「换下一个」。 真正的长期解法是定期巡检（定时任务 + 真实调用），本轮没有做。
· 06_Deploy/worker.js 仍只支持 gemini/openai 且前端调不到它。
· 边界仍然没有变：这些 prompt 依旧一次也没有跑过 Veo 3 / Flow。 （查证时顺带看到：Google 退役表显示 veo-3.0-generate-001 已于 2026-06-30 关停、 veo-3.1-generate-preview 将于 2026-10-22 关停。本项目产出的是给下游用的文本 prompt、 不直接调 Veo API，但下游换模型时值得留意。）

八、元发现

这一轮最值得记的，是我上一轮错在哪、以及错误是怎么被纠正的。

6.8.4 我用「延迟 193ms」这个间接信号，推出了「一个 Key 都没配」这个结论， 并把它当成事实写进了报告。这是错的。 正确的做法本该是直接测量，而不是从一个侧面数字反推。

而纠正它的，正是我为了回答这个问题而新建的自检接口 ——
我造的工具，上线后第一个证伪的就是我自己的诊断。

这比「工具好用」更有价值：它说明这个工具真的在测量事实，而不是在复述我的猜测。 一个只会确认你已有想法的工具，是没有价值的。

由此得到一条比 6.8.4 更硬的教训：
凡是能直接测量的，就不要用间接指标去推断 —— 哪怕推断看起来很合理。 延迟、日志、用户描述，都是间接信号；只有探测是直接的。

还有一层，和上一轮的「更正必须留痕」一脉相承：6.8.4 我更正了 6.8.3 的一个错误结论； 6.8.5 我又更正了 6.8.4 的。这不是反复无常，而是「每建一层观测能力，就会照亮上一层看不见的地方」。 所以不要怕写结论 —— 但要把结论和它的证据强度绑在一起： 「实测得到」和「由延迟推断」是完全不同量级的证据，不该用同样的语气写。
