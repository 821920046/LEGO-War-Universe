## 2. 严重缺陷（第一性原理定位）

### F1 · `clash`/`enemy` 节拍缺少敌对语义 → 编译期整片抛错（严重）

**现象**：`planner` 在 **n≥12** 时，`compileShot` 抛 `FACTION_CONFLICT_INVALID`，整个「编译脚本」面板崩掉。n=4/8 正常，所以极易漏测。

**根因（第一性原理）**：
`selectBeats` 的 `clash` / `enemy` 类节拍会把**正反双方同时写进 `subjects`**；而 `validateShotSpec` 的规则是「对立阵营同框时，`action` 必须含交战语义，且不得是协同语义」。这两条约束分别写在两个文件里，**没有任何一处强制它们彼此一致**：

- `clx-clash-1` 的 action 写作「双方火力在几米内**对轰**」——`对轰` 不在 `COMBAT_ACTION_REGEX` 里；
- `clx-clash-2` 的 action 写作「贴身**缠斗**…**硬撼**」——同样不在。

n=4/8 时这两条节拍没被选中，所以问题被掩盖；n=12 时 climax 阶段要 3 条节拍，命中它们，直接抛错。

**修复**：

1. 修正两条节拍文本，使其显式包含 `交战` / `对抗` 语义，并在源码处留下注释说明该不变式；
2. **把不变式变成可执行断言**：新增测试遍历所有 `clash`/`enemy` 节拍，断言 `hasHostileFraming(action)` 为真。这条规则从此不可能再被无声破坏。

**实证**：`planner` 在 8 个主题 × 5 种镜头数（4/8/12/16/24）下全部可编译，`validateShotSpec` 无阻断级错误。

---

### F2 · `selectBeats` 在同一阶段内重复节拍 —— 正是用户抱怨的「重复」（严重）

**现象**：同一叙事阶段出现**完全相同的 action 文本**。

**根因（第一性原理）**：
`selectBeats` 的注释承诺「池子被用尽时循环取用，但同一阶段内绝不重复」，实现却是：

```js
picked.push(pool[k % pool.length] || usable[0]);   // k 超过池长即取回同一条
```

而各阶段的池子大小**严重依赖门控**：

| 阶段 | 全部门控开启 | 无敌人/无僚机/无载具 |
|---|---|---|
| establish | 6 | **2** |
| build | 6 | **1** |
| climax | 6 | 2 |
| resolve | 6 | 3 |

于是：

- 无敌人/无僚机/无载具时，**n≥7 必重复**（build 阶段只有 1 条节拍）；
- 「无敌军时代」（如 Orbital，资产库确实没有反派角色）+ 僚机 + 载具时，**n≥16 必重复**；
- 全部门控开启时，**n≥32 必重复**。

用户「就算自定义内容也还是有很多重复」的反馈，根因就在这里：**承诺与实现不符**。

**修复（第一性原理）**：把「同一阶段内 id 唯一」升级为**结构性保证**，而不是靠池子够大：

- 新增 `phaseBeatPool(phase, opts)` —— 确定性、已过滤、已洗牌的阶段池；
- 新增 `expandBeats(phase, {need, ...})` —— 取 `need` 条，池内取尽后按轮次调用 `deriveBeat(base, round)` **派生变奏**；
- `deriveBeat` 以 `fnv1a(base.id) + round` 决定「前置机位短句」与「后置质感后缀」，产出 `id = base~v{round}`、**文本不同**的变奏节拍；
- `selectBeats` 改为按阶段调用 `expandBeats`，并保留一条带 id 去重 + 轮次上限的兜底路径。

**实证**：新增扫描测试覆盖 **4 种门控组合 × n=1..40**，断言「阶段内 id 唯一」且「阶段内 action 文本唯一」，全部通过。

## 3. 中危缺陷

### F3 · 电影转译固定 `limit: 4`，大镜头数时退化为复制策展桥段（中）

**根因**：`cinema-homage` 的 `expansionFor(phase, k)` 固定按 `limit: 4` 取扩展节拍，`[k-1] || null`；当某阶段镜头数超过 5 时取到 `null`，该镜头回落成 `curated.action`——**与 k=0 的策展镜头共用同一句 action**。

**为什么没被发现**：`transpileMovieToLego` 末尾调用了 `diversifyShots`，它会给撞车的 action 追加不同后缀，于是**可见文本看起来是唯一的**，底层节拍重复被掩盖。

**修复**：先按与主循环完全一致的公式预计算 `phaseCounts`，据此请求**足量**扩展节拍；把主循环里的重复声明改名为 `phaseCursor`（否则构成同作用域重复声明，又是一次白屏级事故）。

**实证**：n=4/8/12/16/24/32 全部「动作唯一 + 无阻断级校验错误 + 全部可编译」。

---

### F4 · CSV 导出存在公式注入面（中，安全）

**根因（第一性原理）**：Excel / WPS 打开 CSV 时，**加引号并不能阻止公式解析**——`"=1+1"` 会被还原成 `=1+1` 并按公式求值。而本表里的「中文动作分镜脚本 / 生图 Prompt / 生视频 Prompt」在云端模式下来自大模型，属于**不可信输入**。模型一旦吐出 `=HYPERLINK(...)` 之类文本，用户打开表格即执行。

**修复**：新增 `neutralizeCell()`，对以 `= + - @ \t \r` 开头的单元格前置单引号，强制 Excel 按文本处理（Excel 会隐藏该前导引号，不影响观感）。

**实证**：新增测试注入 `=HYPERLINK("http://evil.example","点我")` 与 `+1+1`，断言导出结果中不存在以 `=` / `+` 开头的裸单元格。

## 4. 低危缺陷

### F5 · 原创立意句存在病句（体验）

**现象**：主题是完整句时，被直接当作句子的主语，拼出
「现代的城市废墟，**特战小队在城市废墟中执行夜间突袭，营救被困飞行员被投入**一场争分夺秒的搜救任务」。

**根因**：`buildOriginality` 无条件 `subject = theme`。立意层是本轮「像智能」的门面，病句直接削弱说服力。

**修复**：按主题长度分流——短主题（≤14 字）作主语；长主题作为独立「背景句」，主句改用「这支小队被投入…」；无主题时也有完整通顺的句子。

### F6 · 语法门禁跳过 `public/`（门禁覆盖）

`SKIP_DIRS` 曾把 `public/` 排除在外。目前 `public/` 只有 `build-manifest.json`，暂无实际缺口，但若将来有人往里放 JS，门禁会**静默漏掉**。已把 `public` 纳入 `ROOTS` 扫描面。

### F7 · 一条后端测试是「空断言 + 自相矛盾」（测试自身失效）

`never injects an opposing asset into a non-combat shot` 的夹具是 **3 个全部非战斗的镜头**，却同时断言：

```js
assert.ok(opposingIds.length > 0);          // 要求名册里必须有敌人
// … 又要求任何镜头里都不许出现敌人
```

两者不可能同时成立——它要么永远失败，要么（在旧夹具下）因为「一个敌人都没注入」而让后半段断言**恒真、形同虚设**。

**修复**：改为 4 镜混合夹具（静默潜行 / 集结待命 / **并肩**交战 / 正面交战），同时断言：

- 前 3 镜**绝不**出现敌人（含「并肩交战」这种含交战词但属协同语义的陷阱）；
- 第 4 镜**必须**出现敌人（证明注入逻辑本身有效，避免空断言）；
- 全部镜头均不触发 `FACTION_CONFLICT_INVALID`。

## 6. 残余风险（红队视角，明确保留）

1. **治理仍是确定性关键词护栏，不是语义审核（中）**
   已覆盖 NFKC / 同形字 / leet / 零宽字符 / 逐字插分隔符 / 英文词形（torture·tortured·genocide·genocides·decapitation·decapitated）。但仍存在同类字形绕过，例如 `putln`（小写 L 冒充 i）当前放行。
   **为什么故意不修**：经验证，把 `l → i` 加入全局同形字归一**会破坏既有检测**——`al qaeda` 在正文里是两个词元（`al`+`qaeda` → 拼接 `aiqaeda`），而词条 `al-qaeda` 是单次归一（→ `aigaeda`），两者不再相等，`al qaeda` 反而漏检。**修一个绕过换来一个漏检，不划算**。正确做法是引入独立的语义审核通道，而不是继续堆字符映射。

2. **环境资产的「时代不一致」仍会产生提示级告警（低）**
   资产库各时代环境覆盖极不均衡（Modern 45 个、Modern High-Tech 1 个），因此 `environment` 的时代不一致被设计为 `warning` 而非 `error`。例如「伊拉克战争」题材可能选到 Modern 环境。这是**有意的诚实降级**（`ERA_SEVERITY_BY_KIND` 已注释说明），不是缺陷。

3. **超长片的节拍多样性受模板库规模限制（低）**
   当镜头数超过模板库容量时，靠 `deriveBeat` 派生变奏保证「文本不重复」。文本确实不同，但底层戏剧节拍仍是同一族的派生。这是手写模板库的固有上限，进一步提升需要继续扩充 `BEATS`（本轮已新增 8 条 hero 节拍，把 hero-only 池从 1~3 条提升到 3~5 条）。

4. **电影转译的策展桥段与扩展节拍风格略有落差（低）**
   扩展节拍来自通用 `BEATS`，策展桥段来自 `CINEMA_DATABASE`，两者语感不完全统一。属内容质量问题，非功能缺陷。

# 第二轮对抗审查 · 戏剧功能轴（版本 6.4.1）

> 触发：用户第二轮反馈 —— 「生成的视频脚本里面动作太单一了，完全不能构成电影，请重新优化。」
> 这一轮比第一轮更深：第一轮是**文字重复**（同一句话复制多遍），这一轮是**戏剧功能重复**（文字各不相同，但每一镜在故事里干的是同一件事）。
> 方式：源码走读 + 第一性原理定位 + 可执行探针（临时脚本，跑完即删，不随仓库发布）+ Playwright 真实浏览器实证

## 10. 根因：只有一根轴，缺了第二根

第一轮修的 `focus`（hero / squad / vehicle / clash / enemy）回答的是「**谁**在画面里」，并决定哪些占位符合法。但它**回答不了「这一镜对故事做了什么」**。

于是「按 focus 选节拍」的结果必然是：每一镜都是「一个战斗员执行一个战斗动作」。文字可以千变万化（`diversifyShots` 还能再加后缀），但戏剧上是同一件事的 N 次重复 —— 那是**蒙太奇**，不是电影。

**电影需要的是第二根轴：戏剧功能 `fn`。** 交代目标 / 建立人物 / 制造静默 / 给出反应 / 揭示情报有变 / 逼迫抉择 / 兑现代价 / 完成反转。

探针输出（修复前）：

```
电影模式 · 相邻两镜功能不重复  ✗  ← 🌍 铺陈规模 / 🎯 交代目标 / 📈 压力升级 / 🗺️ 临场计划
                                    / 💥 正面交锋 / 📈 压力升级 / 🏚️ 残局 / 🏚️ 残局
```

根因：resolve 阶段的**策展镜头** `fn` 取固定的 `CURATED_FN_BY_PHASE['resolve'] = 'aftermath'`；而**第一个扩展节拍**按 `PHASE_ARC.resolve` 取，首项同样是 `aftermath`。两者相邻 → 撞车。

这一条**只有真实浏览器冒烟能发现**：单元测试只覆盖 `selectBeats`（本地规划器路径），而 `transpileMovieToLego`（电影致敬路径）走的是「策展镜头 + 扩展节拍」的混合编排，两条路径的 `fn` 分配逻辑不同。**这正是「单测全绿 ≠ 页面正确」的又一例**，也是本轮把 Playwright 冒烟纳入常规验证的理由。

修法（两层）：
1. **源头**：把策展镜头的 `fn` 作为 `prevFn` 传进 `beatsForPhase`，第一个扩展节拍自然错开。
2. **兜底**：`tagDramaticFunctions()` 作为三条路径（本地规划器 / 电影致敬 / 云端大模型）**共用的强制不变式**，保证「相邻两镜不同功能」在任何路径下恒成立。

## 12. 单调兜底的一个反直觉点（第一性原理）

`tagDramaticFunctions` 里，「单调检测」**必须先于**「相邻去重」执行。

如果反过来先做相邻去重，一段「8 镜全程对轰」会被打散成 `对轰/非对轰/对轰/非对轰/…` —— 看上去相邻不同了，**但一半镜头仍在交锋**，仍然是蒙太奇。这只是把单调藏了起来，不是消除它。

正确做法：先按「推断出的功能种类 ≤ 2」判定整片单调，若成立则**按各阶段弧线整体重排**（8 镜 → `goal/character/plan/contact/escalate/clash/aftermath/reaction`，只剩 1 镜交锋），再做相邻去重收尾。

这个顺序问题是我自己写的第一个版本里的真实缺陷 —— 单元测试直接把它暴露了出来（单调兜底成了**不可达代码**）。

## 16. 残余风险（红队视角）

1. **`inferFunction` 是关键词启发式**，不是语义理解。它只用于给**云端模型返回**的镜头补标 `fn`（本地路径的节拍自带真实 `fn`）。启发式误判会让徽标文案与画面略有出入，但**不会**破坏「相邻互异 / 整片多样」这两条真正影响观感的不变式。
2. **`tagDramaticFunctions` 的重排只改 `fn` 标签，不改 `action` 文本**。在极端单调输入下，重排后的 `fn` 与文本可能不完全对应（例如一段被标成「反应」的对轰文本）。这是**有意的取舍**：宁可在云端模型彻底偷懒时保住「像电影」的结构，也不放任输出一段 8 镜对轰。真正的解法是模型自己按【最高优先级五】产出多样功能。
3. **时长档位依赖模型 profile**（4/6/8）。若某 profile 只支持单一档位，编译器会钳制，节奏起伏会消失 —— 这是 profile 的能力边界，不是引擎缺陷。
4. **功能种类与镜头数的关系**：n ≤ 4 时弧线只覆盖 4 种功能（受阶段数限制），属正常；n 越大越丰富（n=16 可达 15 种）。

## 17. 后续建议（第二轮）

1. 把 `fn` 的**语义一致性**纳入治理：检查「声明为 `quiet` 的镜头是否真的没有交战语义」，把 G3 那类「声明与内容矛盾」的不变式补齐。
2. 让云端模型返回 `fn` 后做一次**语义回验**（用 `inferFunction` 交叉验证），偏离时记录遥测，用于评估【最高优先级五】的实际遵从率。
3. 为 `PHASE_ARC` 引入**节奏模板**（`rhythmTemplates` 已存在于 `index.html` 的数据块中，目前未接入叙事引擎），让「预告片 / 纪录片 / 史诗」三种节奏真正影响功能分配。

>

## 18. 缺陷 G1（严重）：`selectCast` 收到了 `theme`，却从未解构它

- **症状**：`selectCast(r, { era, task, theme, setting })` 的三个调用点（`planner.js` / `cinema-homage.js` / `ai-brain.js`）都规规矩矩地把 `theme` 传了进去，函数签名里**却没有 `theme`**。载具于是永远取 `rank(...).slice(0, 3)`，而 `rank` 在没有域信号时退化为 **ID 升序** ⇒ 取到的是资产库里 ID 最小的三台。
- **实证**（探针输出，修复前）：`「核潜艇在深海猎杀敌方舰队」` → `KC-46 空中加油机 | 刚性充气突击艇 | 装甲通用越野车`；且**每一个现代题材拿到的都是同一组**。
- **为什么危险**：这是一个「参数被静默吞掉」的缺陷 —— 类型系统不会报错，单测不会报错，代码看起来完全正确（调用点全都传了）。它只在**跨题材对比**时才暴露。
- **修法**：`DOMAIN_RULES` 四域路由 + `domainScore`（类别 +10 / 域词 +4）+ `pickDiverse` 类别去重。

## 19. 缺陷 G2（严重）：`taskAffinity` 的裸 `tank` 命中了 `Tanker`

- **症状**：combat 分支写的是 `/special|assault|infantry|tank|突击|特战|步兵|装甲|坦克/`。裸 `tank` 命中 `KC-46 **Tank**er`，于是**空中加油机成了所有现代战斗题材里排名第一的载具**。
- **为什么危险**：这是典型的「正则不加词边界」缺陷，而且它**恰好把 G1 的症状伪装成了合理结果** —— 修复 G1 之前，加油机排第一看起来像「ID 排序的偶然」，掩盖了 G2。两处缺陷叠加时，只修一处都不够。
- **修法**：`\btank\b` / `\barmou?r\b` 加词边界，并补 `special|assault|infantry`。

## 20. 缺陷 G3（严重，最致命）：规划器几乎不让载具上镜，且会跳过主载具

这是本轮最重要的发现 —— **它让 G1、G2 的修复也无法被用户看见**。

- **症状 A（载具镜轮不到）**：`PHASE_ARC` 把 `goal / character / plan / contact / aftermath` 这类通用功能排在弧线前段，而 `focus='vehicle'` 的节拍恰好都落在 `observe / approach / escalate / close` 这些**靠后**的功能上。`expandBeats` 按 `arc[k]` 取功能，n=8（每阶段 2 镜）只走到 `arc[0]`、`arc[1]` ⇒ 载具镜基本轮不到。实测 n=8 的「核潜艇」题材：**一台载具都没有**。
- **症状 B（主载具被跳过）**：即便轮到载具镜，载具是 `vehicles[i % vehicles.length]` —— **按镜头序号取模**。载具镜若落在 i=1，`vehicles[1]` 上镜，而 `vehicles[0]`（选角引擎按「战场域 + 题材点名度」排出来的**题材点名的那台**）永远轮不到。实测「F-22 战斗机高空制空巡逻」：上镜的是 `AIR-914 RQ-4 全球鹰侦察机`，**F-22 一次都没出现**。
- **为什么单测抓不到**：`selectCast` 单测（我新加的）验证的是**返回值**，返回值里 F-22 排第一，测试全绿。缺陷在**下游**（`selectBeats` 的 focus 分配 + planner 的取模），是**跨模块**的。这正是第二轮总结的教训「单测是按模块的，缺陷往往是跨模块的」的再次应验 —— 而且这次连「浏览器冒烟」第一版都骗过了：我最初的冒烟断言用 `/潜艇/.test(outputText)`，而输出里的 **`CHR-904 弹道导弹核潜艇艇长`** 是个人物，**断言假阳性通过**。直到改为「从定妆表里提取真实载具 ID」才暴露。
- **修法（三层，均不破坏既有不变式）**：
  1. `takeByFn` 在同一功能有多个候选时优先选载具镜（n=4 也能自然出现载具）。**fn 不变 ⇒ 戏剧弧线不受影响。**
  2. 若整片仍无载具镜，把某一镜**换成同 fn 的载具镜**（同上，fn 不变 ⇒ 「相邻功能互异」自动保持）；守卫：不得把**仅剩的**敌我对峙镜换掉，否则就成了「没有敌人的战争片」。
  3. `planner.js` 载具改用**独立游标**，只在真正用到载具时前进 ⇒ `vehicles[0]` 必定先上镜。

## 21. 缺陷 G4（中）：`submarine` 守卫是不可达死代码

`planner.js` 的 `vehicleFitsEnv` 与 `shot-spec.js` 都写了 `class === 'submarine'` 的分支，但**资产库里没有任何资产是潜艇** —— 三艘既有潜艇（`SHP-402` / `SHP-603` / `SHP-802`）全被标成 `class: "ship"`。守卫写得再对，也永远不会执行。

- **为什么危险**：「守卫存在」≠「守卫生效」。这类死代码给人**虚假的安全感** —— 读代码的人会以为「潜艇在荒漠」已经被防住了。
- **修法**：三艘潜艇改标 `class: "submarine"`；把 `submarine` 加进**三处**硬编码枚举（`validate.py` / `assets.schema.json` / `asset-forge.js`）；补 `motions.submarine` 保持数据自洽；新增**跨模块一致性测试**断言三处枚举同步。

## 27. 缺陷 H4（严重）：`pickDiverse` 只认类别、不认战场域

加完资产后跑探针，发现新装备根本没按题材走：

```
二战北非沙漠装甲追击 → IS-2 坦克 | 埃塞克斯级航母 | P-51   ← 沙漠装甲战里有一艘航母
中途岛航母对决       → 埃塞克斯级航母 | 克伦威尔坦克 | F6F ← 航母对决里有一辆坦克
```

根因是 6.5.0 引入的 `pickDiverse()`：**同类只取一个**。这条规则在域内是对的（避免三台全是主战坦克），但它**先于战场域生效** —— 排序已经把舰艇排到了最前，多样性规则却跳过第 2、3 艘舰，去抓第一个「其它类别」，于是每个陆战题材都配一艘航母。这是典型的「次级优化目标压过主目标」。

修法是把次序改成域感知四段式：域内每类一个 → **域内放开重复继续补**（中途岛要的是三艘舰，不是「一舰一坦一机」的伪多样性）→ 其余类别 → 原顺序兜底。

**这里还踩了一个自己的坑**：补位阶段写成 `if (used.has(a.id)) continue`，但第一步只登记了「类别」、没登记 ID，同一艘航母会被推两次（`埃塞克斯 ×2`）。必须加 `out.includes(a)`。已由测试 `选角结果内不得出现重复载具` 锁死。

## 28. 缺陷 H5（严重）：纪元兼容不等于战区兼容

`ERA_COMPATIBILITY` 里 `WWII ⇄ Pacific` 是合理的（同属二战），但**战区不能混**。资产库补全日军之前，太平洋题材唯一的敌军就是德军 —— H1 就是这个的直接后果。

修法刻意保守：新增 `theaterOf()`，只有**资产与题材双方**都带明确战区标记、且两者冲突时才剔除。因此：

- 「太平洋 / 中途岛 / 硫磺岛」→ 剔除德军 ✅
- 「诺曼底 / 斯大林格勒 / 柏林」→ 剔除日军 ✅
- 「北非沙漠装甲追击」→ 双方都无战区标记，德军（非洲军团）照常上镜 ✅

最后一条是必须的：一刀切会把隆美尔的非洲军团也误杀。

## 29. 缺陷 H6（中）：敌方载具放行条件的假阳性

`bySide(vehicles,'coalition')` 挡死了所有敌方平台（H3）。但**不能简单地全放开** —— 那会把伊军 T-72 当成联军英雄载具推上镜头。

第一版放行条件写成 `themeMatch(a, theme) >= 9`（最长公共子串 ≥ 3 字），立刻被现实打脸：

```
伊拉克战争费卢杰巷战 → 伊拉克 T-72 坦克 | 伊拉克 T-72 坦克 | M1A1
```

题材里的「伊拉克」与资产名共享 3 字，敌方 T-72 被当成英雄载具，而且排到了第一。**这比不放行更糟** —— 不放行只是拍不了，放行错则是成品穿帮。

修法是加阵营停用词层（`themeNamesAsset()`）：最长公共子串 ≥ 3 **且不是阵营/国名词**。

- 「T-72 坦克战」→ 子串「t72坦克」→ 放行 ✅
- 「虎式坦克对决」→ 子串「虎式坦克」→ 放行 ✅
- 「伊拉克战争费卢杰巷战」→ 子串「伊拉克」→ 停用，不放行 ✅

**教训**：放行类规则必须配反例测试，只测正例会漏掉更严重的假阳性。

## 30. 缺陷 H7（严重，最隐蔽）：时代识别顺序让整个纪元资产池失效

这一条是加完资产、跑探针时**意外**发现的：

```
海湾战争夜战防空导弹阵地伏击  [intent.era=Modern]
```

`INTENT_RULES` 是顺序敏感的，`['Modern', /现代|特战|无人机|夜战|.../]` 排在 `Gulf War` / `WWII` / `Pacific` **之前**，而匹配用 `if (!out[key])` 先到先得。题材里的「夜战」命中 Modern 就把 era 锁死了 —— 于是**海湾战争、二战、太平洋三个纪元的资产池永远进不了片**，加多少资产都没用。

这条最值得记：它不是资产库的问题，而是**上游一个与资产无关的顺序 bug，能让下游所有资产投入归零**。修法是具体优先、Modern 兜底，并顺手补全 WWII / Pacific 的关键词（斯大林格勒、硫磺岛、冲绳、塞班、中途岛）。

## 33. 残余风险（红队视角，第四轮）

1. **战区互斥是「文本标记」层面的，不是知识层面的。** 判定依赖资产/题材里出现「德军 / 日军」这类字面词。一个叫「Axis Infantry」而没有任何战区字样的资产不会被拦。当前库内所有轴心国资产都带中文字样，因此安全；后续新增资产必须沿用这一约定。
2. **`themeNamesAsset` 的停用词表是封闭枚举。** 新增国家/阵营（如「叙利亚」「利比亚」）需要同步补表，否则会重现 H6 的假阳性。
3. **`INTENT_RULES` 仍是「先到先得 + 顺序敏感」。** 本轮只修了顺序，没改成打分制。两个具体纪元同时命中时（如「二战太平洋」）仍由顺序决定（WWII 在前）。
4. **Orbital 载具仅 7 件、Gulf/Iraq 载具 21 件**，仍远少于 Modern 的 132 件。纪元间不再「有和无」的差别，但仍是「多和少」的差别。
5. **`enemyFallback` 现在在所有纪元都为 false**，但它的兜底路径因此失去了真实覆盖 —— 若将来某纪元的敌军资产被误删，测试会红，这是期望行为；但要留意不要为了让 `enemyFallback` 变 false 而放宽纪元兼容。

## 34. 第一性诊断：用户抱怨的不是「资产少」，是「引擎里没有故事」

前两轮（6.5.0 / 6.6.0）都在加资产。本轮先把成片原文打出来读，结论是**加资产永远修不好这条反馈**。随手一部 8 镜片：

```
[1] 特写  【MERIDIAN】动力外骨骼特战队员 在废墟里推进…
[3] 中景  【MERIDIAN】动力外骨骼特战队员 沿掩体边缘前移…
[5] 全景  战斗爆发，双方交火…
```

三条根因互相独立：

| # | 根因 | 可验证的表现 |
| --- | --- | --- |
| A | **没有人物** | `{heroCallsign}` 展开是「【MERIDIAN】动力外骨骼特战队员」——**单位类型**，不是人 |
| B | **没有因果** | 逐镜扫描，**没有任何一镜引用上一镜的结果**；节拍是并置的卡片 |
| C | **没有题材** | 逐镜扫描，正文里除 `{env}` 外**没有一个题材名词**；二战/现代/海战正文同构 |

**教训**：当用户说「内容单一」时，不要先怀疑数据量。把**最终产物原文**打出来读一遍，比看任何中间指标都快。前两轮之所以没发现，是因为一直在检查「资产有没有上镜」，而没检查「上镜之后讲了什么」。

## 35. 缺陷 S1（严重）：`{link}` 占位符泄漏到成片正文

因果连接词由 `linkFor()` 提供，首镜或不需要承接时返回空串。而 `renderTemplate()` 的设计是**对空值不做替换**（它要保留未提供的占位符以便排查），于是正文里出现裸的 `{link}`：

```
[2] 中景  {link}【DELTA】沃尔科夫从胸袋里摸出一张被汗浸皱的照片…
```

这个 bug 在引入连接词的第一分钟就会出现，且**只在「连接词为空」时触发**，很容易被「看起来有连接词」的样本掩盖。

修法：`planner.js` 里包一层 `linkable()`，连接词为空时把 `{link}` **整段删掉**（而不是留空串）。

**教训**：一个「保留未提供占位符以便调试」的设计，在把它自己的可选参数喂进去时会变成 bug。凡是 `{xxx}` 可能为空的场合，都要在渲染前显式清理。

## 36. 缺陷 S2（严重，能整片抛错）：新增节拍的正文没过交战语义校验

新增 `observe` 的海军/空军变体时，海军那条写成了：

> `…{heroCallsign}没有下令**攻击**，只是报出方位和距离。`

`COMBAT_ACTION_REGEX` 里有「开火 / 交火 / 交战 / 拦截 / 伏击 / 压制…」，**没有「攻击」**。于是 focus = `enemy` 的这一步在校验阶段被判为「对立阵营同框却无对抗动作」，`compileShot` 直接抛 `FACTION_CONFLICT_INVALID`。

触发条件是 **n = 24 的诺曼底片第 12 镜** —— 只有镜头数足够多、队列消耗到这条变体时才会撞上。单跑 8 镜永远绿，全量测试里才红。

修法两条：

1. 正文改为「没有下令**开火**」；
2. **新增回归断言**：遍历全部 10 个原型的全部骨架步骤，凡是 focus 为 `clash` / `enemy` 的，必须 `COMBAT_ACTION_REGEX.test(action)` 且 `hasHostileFraming(action)` 为真。这把「新增节拍忘了过校验」变成编译期就能发现的错误。

**教训**：校验器与内容库是两份独立数据，**任何新增内容都必须被内容级测试覆盖**，不能只依赖「跑一遍端到端看有没有崩」。

## 37. 缺陷 S3（中）：赌注是名词短语，读不成句

`urban-raid` 的 `stake` 原为「整场行动的主动权」（名词短语），而模板是「…{objective}——否则{stake}。」于是拼出：

> `必须在天亮前的四十分钟之内摸进敌方指挥掩体——否则整场行动的主动权。`

没有谓语。同类问题还有 `general-combat` 的 `deadline = '天亮前'` 与模板「{deadline}之内」拼出**「天亮前之内」**（同义反复）。

修法：`stake` 一律改写成完整小句（「己方会在接下来的巷战里彻底失去主动权」），`deadline` 一律写成可与「之内」搭配的时长短语（「天亮前的一个小时」）。并在测试里加一条**形态断言**：logline 里不得出现 `——否则` 后紧跟句号或不足 6 字的片段。

## 38. 缺陷 S4（中，一眼假）：敌我共用姓名池，中东战场的敌方指挥官叫「桥本」

`PERSONA_NAMES` 此前只有一个 `default` 池，且混编了各国姓名：

```js
default: ['米勒', '科瓦奇', '施密特', '桥本', '杜兰', '哈里斯', '罗西', '阿隆']
```

后果一：一部现代题材里「我方突击队长」与「敌方指挥官」从同一个池子抽名字，**两个米勒同框**。
后果二：`nationOf()` 判不出「伊拉克指挥官」的国籍（当时没有 `iraqi` 规则），落进 `default` 池，于是**中东战场的敌方指挥官抽到日式姓名「桥本」**。

三层修法：

1. 新增 `iraqi` 国籍规则与姓名池（`伊拉克|共和国卫队|萨达姆|复兴党|iraqi|iraq|republican guard|saddam|baath`）；
2. 兜底池**按阵营拆开**：`defaultFriendly` / `defaultOpposing`，国籍判不出来时至少阵营不能混；
3. 新增 `dominantNation()`：一方之内没标国籍的同伴，按**本方多数国籍**补姓名池（海湾战争的我方一水儿美军、敌方一水儿伊拉克人），并把推断结果**回填**到 `entry.nation` 供定妆表显示。

## 39. 缺陷 S5（中，最隐蔽）：`\bcrew\b` 把航母甲板兵判成陆战装甲车组

`DOMAIN_RULES.ground.charRe` 里写了裸 `\bcrew\b`，命中 `Carrier Deck Crew`：

```
海湾战争夜战防空导弹阵地伏击  domain=ground
  航母甲板人员（黄衫）  ground.charRe 命中 \bcrew\b → +10   ← 拿到与坦克车组同等的分
  阿帕奇飞行员          ground.charRe 不命中     →  0
```

结果：**一个航母甲板兵被选进沙漠导弹阵地，第 7 镜里站在打空的阵地上收枪**；真正的飞行员反而被挤出去。

值得注意的是 `ARCHETYPE_RULES` 里**早就踩过同一个坑**，注释写得很清楚：

> `// \`crew\` 不加边界会命中 "Screwdriver"，\`ship\` 会命中 "Leadership"，同理加边界/换词`

但 `charRe` 是后加的，重复了同一个错误。修法：改为只认与装甲明确连用的组合（`tank ?crew` / `armou?red ?crew`）。

**教训**：同一份代码库里，**同一个错误可以在两个不同的表里各犯一次**。加新表时应当先扫一遍同类表的注释。

## 40. 缺陷 S6（中）：跨域惩罚 + 裸 `strategic` 把「战略轰炸机机组」罚出空战域

为了让「候选池凑不满时按 ID 升序硬填」不再把无关角色塞进片子，新增了跨域惩罚。但 `strategic.charRe` 里的裸 `strategic` 命中了单位名 `Strategic Aviation`：

```
B-2 轰炸敌方雷达站  domain=air
  战略轰炸机机组  air +10，strategic（"Strategic Aviation"）→ −6 ⇒ 4
  无人机操作员    air +10，无跨域                        ⇒ 10   ← 主角变成无人机操作员
```

修法：`strategic.charRe` 只认真正与导弹/火箭连用的组合（`strategic (?:rocket|fires|missile)`）。同一轮还发现 `air.re` 漏了「轰炸」——「B-2 轰炸敌方雷达站」识别不出战场域，选角整体退化为按 ID 升序硬填，一并补上。

**跨域惩罚的权重设计**：扣 6 而不是扣满 10。必须**小于**本域命中分，否则「舰队题材里的舰载机飞行员」这类合法的跨域兵种（naval + aviation 双命中）会被自己人挤掉。载具不做这一步：载具的 `class` 已经是强信号（+10），再罚会误伤合法跨域资产。

## 41. 结构性空洞 H8（与 H1 同类）：现代题材的反派只有三个人

`ERA_COMPATIBILITY` 把 `Modern` 与 `Gulf War` / `Iraq War` 隔开，而 Modern 一系的反方角色只有：

```
CHR-412 便携防空导弹射手   CHR-619 游击火箭筒手   CHR-906 导弹发射控制军官
```

于是：

> 「核潜艇深海猎杀」的反派是**扛火箭筒的游击队员**；「F-22 制空巡逻」的反派里有一个**战略导弹发射控制军官**。

这与 6.6.0 的 H1（太平洋题材唯一敌军是德军士兵）**完全同类**：不是「少」，是「错」。补法同上一轮 —— 数据驱动补包：

- `modern-opfor-pack`（CHR-909…924，16 项）：敌方隐身战斗机飞行员 / 武装直升机飞行员 / 防空营指挥官 / 核潜艇艇长 / 驱逐舰战情军官 / 海军陆战队员 / 坦克车长 / 机械化步兵 / 反坦克导弹射手 / 特种部队队员 / 狙击手 / 战地指挥官 / 电子战操作员 / 战斗工兵 / 导弹旅指挥官 / 空降兵；
- `modern-aircrew-pack`（CHR-925/926，2 项）：现代战斗机飞行员、现代多用途战机飞行员（此前现代空战题材**没有**任何战斗机飞行员角色）。

## 42. 可观赏性改造：从「通用模板」到「域感知 + 人物锚点」

# 第七轮对抗审查（6.7.1 · 遗留清理）

本轮没有新功能，只清 6.7.0 明确记下的技术债。清理过程中又挖出三处此前未被发现的结构性缺陷 —— 说明「遗留清单」本身也需要被对抗性复核，而不是照着清单逐条划掉。

## 46. 收尾特写共用：从「概率上可能撞车」到「结构上不可能」

**原状**：`reaction`（收尾反应特写）是**共享质感节拍**，每个战场域只写 2–3 个变体，靠 `fnv1a(theme) ^ fnv1a(arc)` 做确定性轮转。同一战场域的两个原型仍有概率抽到同一句，测试里显式放行了「最多 1 句」。

**根因**：共享池 + 哈希轮转本质上是一种**避免撞车的启发式**，而不是**消除撞车的结构**。变体数少于同域原型数时，鸽笼原理决定了必然存在碰撞。

**修法**：把收尾从共享池搬进原型骨架 —— 10 个原型各写一条 `reaction`，与已经单写的 `close` 并列。`storySteps` 的装配顺序是 `[...own, ...sharedOrdered]`，原型专属步骤永远排在共享步骤之前，因此新写的 `reaction` 必然被选中，共享池里那条退化为永不触达的兜底。

**验证**：测试从 `shared <= 1` 收紧为 `assert.equal(shared, 0)`，并去掉「只允许 reaction 重复」的放行分支。20 题材批量扫描跨原型逐字重复 1 → **0**。

## 47. 轨道战场域不可达：一批「写了但永远不生效」的内容

**原状**：`story.js` 的 `TEXTURE` 里写了 6 条 `domains: ['orbital']` 的质感节拍（世界镜头、人物时刻、接近、观察、静默、收尾），`planner.js` 的 `ENTER_VERB` 里也备好了 `orbital: '进入'`。

**根因**：`roster.js` 的 `DOMAIN_RULES` 只有 `naval / air / strategic / ground` **四个域，根本没有 `orbital`**。`domainOfText('近地轨道空间站失压事故')` 因此返回 `null`，于是：

- 那 6 条轨道节拍**永远不可能被选中**（`matched` 恒为空），是纯粹的**死代码**；
- 轨道题材的 `{place}` 落到陆战环境兜底（`'urban|city|desert|street|城市|巷战|沙漠|山地'`）；
- 轨道题材的选角拿不到域加分，退化为按 ID 升序硬填。

**修法**：

1. `DOMAIN_RULES` 新增 `orbital` 域，且**必须排在 `air` 之前** —— 「太空战机」含「战机」、「轨道轰炸机」含「轰炸机」，排在 `air` 之后会被 `air` 截走。
2. `planner.js` 的环境兜底补上 orbital 分支（`'空间站|轨道|太空|失重|零重力|气闸|舱外|月面|station|orbital|zero-g'`）。

**验证**：新增测试断言轨道题材的 `plan.story.domain === 'orbital'`，且成片正文里真的出现本域节拍（「舱体外壁」「地球的弧线」「真空」）。

**教训**：一个「没有测试覆盖的配置分支」和一个「不存在的能力」在运行时完全等价。`TEXTURE` 里写了 orbital 变体、`ENTER_VERB` 里写了 orbital 动词，两处都「看起来支持轨道」，但判定层没有这个域 —— 三处各自单独看都没问题，合起来是空转。**枚举型配置必须有一条「每个取值都能被生产出来」的测试。**

## 48. 国籍判定三处误标：`陆战队`、战区括号、以及敌我同国籍

这三处都是同一个动作暴露出来的：6.7.1 把 `nationLabelOf()` 显示到了定妆表卡片上。**此前国籍只参与姓名池选择，不显示，所以错了也看不见**；一旦显示，「反方势力 · 美军」立刻是一眼假。

### 48.1 裸 `陆战队` 不是美国专有

`NATION_RULES` 的 `us` 规则里含 `海军陆战队|陆战队`。命中它的 8 个角色里只有 4 个真的是美军：

| 资产 | 实际阵营 | 旧判定 | 正确判定 |
| --- | --- | --- | --- |
| 美国海军陆战队员（伊拉克） | Coalition | us | us ✓（靠「美国」） |
| 美国海军陆战队步枪手 | Allies | us | us ✓（靠「美国」） |
| 美军海军陆战队喷火兵 | Allies | us | us ✓（靠「美军」） |
| 海军陆战队步枪手（NATO） | NATO | us | null（国籍不可判定） |
| **敌方海军陆战队员**（Adversary Naval Infantryman） | Opposing Force | **us** ✗ | null |
| **敌方轨道陆战队员** | Opposing Force | **us** ✗ | null |
| **轨道陆战队医务兵**（Orbital Corpsman） | Coalition | **us** ✗ | null |
| **轨道陆战队员**（Orbital Marine） | Coalition | **us** ✗ | null |

真正属于美军的资产都带显式标记（美国 / 美军 / usmc），因此删掉裸 `陆战队`、保留 `美(?:国|军)海军陆战队` 即可。

### 48.2 括号里的「伊拉克」是战区，不是国籍

「联军战斗医护兵（**伊拉克**）」是在伊拉克作战的联军医护兵。旧规则把括号内容算进国籍判定，于是「伊拉克战争城市清剿」里我方联军被标成**伊军**、与敌方同国籍 —— 定妆表上我方和敌方都是伊军，直接自相矛盾。

**修法**分两层：

1. **剥掉括号段**再做匹配（`[（(][^）)]*[）)]` → 空格）。括号是战区/批次标注的惯例位置。
2. **把 `伊拉克 / iraq` 降级为弱标记**。`kw` 字段里同样带着战区标签（`联军 医护兵 救护 伊拉克 combat medic`），光剥括号挡不住。因此保留 `共和国卫队 / 萨达姆 / 复兴党 / republican guard / saddam / baath` 作为**强标记**（指向政权，与阵营无关），而 `伊拉克 / iraq` 只在**非友军阵营**资产上作数 —— 友军阵营的「伊拉克」按定义一定是战区。

### 48.3 敌我同国籍：加一条结构性不变量

前两条修的是「判定错了」，但即使判定都对，**推断**仍可能撞车：`dominantNation()` 用「本方多数国籍」给未标记的同伴补国籍，两侧各自推出来的结果可能相同。

因此 `buildRoster` 增加一条守卫：

```js
// 敌我同国籍是自相矛盾的：战争片的对立阵营按定义就不是同一个国家。
if (sideNation.coalition && sideNation.opposing && sideNation.coalition === sideNation.opposing) {
  sideNation.opposing = null;   // 放弃敌方推断，退回 defaultOpposing 姓名池、不显示国籍
}
```

宁可留空，也不能把反方势力标成「美军」。

**验证**：新增 3 条测试（战区括号 / 裸陆战队 / 敌我不同国籍）与 1 条历史题材国籍回归。修复后各题材的敌我国籍：

| 题材 | 我方 | 敌方 |
| --- | --- | --- |
| 伊拉克战争城市清剿 | 美军 | 伊军 |
| 海湾战争夜战防空导弹阵地伏击 | 美军 | 伊军 |
| 诺曼底登陆抢滩 | 美军 | 德军 |
| 中途岛航母对决 | 美军 | 日军 |
| 斯大林格勒巷战 | 苏军 | 德军 |
| 核潜艇深海猎杀 / 轨道空间站失压事故 | （未定） | （未定） |

## 49. 定妆表与剧本正文：两套角色口径合并为一套

**原状**：`character-lineup.js` 自带 `FACTION_TEMPLATES` —— 四套手写的「幽灵队长 / 猎鹰狙击手」阵容，角色编号 `CHR-C01` / `CHR-O01`（**不是合法资产 ID**，注册表里查不到）。于是同一部片子里并存两套口径：

| | 剧本正文 | 定妆表 / 全家福 Prompt |
| --- | --- | --- |
| 角色来源 | 真实资产（`roster.js`） | 手写模板 |
| 角色身份 | `persona` 人物姓名（「邓肯」） | `name` 单位类型（「弹道导弹核潜艇艇长」） |
| 角色 ID | `CHR-904`（可解析） | `CHR-C01`（不可解析） |

后果有两层：定妆表可能展示一支**既不在资产库里、也不在本片里**的队伍；即便走真实名册，全家福生图 Prompt 也会把「潜艇艇长」当成一个人的名字，让模型画出一个没有面孔的角色。

**修法**：

1. **删除整个 `FACTION_TEMPLATES`**。`extractCharacterLineup` 变成 `roster.js` 的适配层：
   - 有分镜 → `buildRoster(shots, registry)`，与剧本正文同源；
   - 无分镜 → `selectCast()` 按题材预选，再喂给 `buildRoster`，形状与真实名册完全一致。
   两条路径都出自同一个选角引擎，因此不存在「预览是幽灵队长、生成后变成邓肯」。
2. **`roster.js` 新增 `displayNameOf(entry)`**，作为全站唯一的角色显示名口径（`persona > name/nameZh > id`）。`labelFor` / `aliasLabel` / 定妆表卡片 / 全家福 Prompt 全部改走它。
3. **时代反推改用资产的 `series` 取众数**。旧实现靠硬编码 ID 前缀猜（`CHR-1xx` → WWII、`CHR-63x` → High-Tech），这些前缀在 6.5 / 6.6 两轮扩容后已大面积失配（`CHR-63x` 区间根本不存在），基本一个都命中不了，等于没有推断。
4. **`rosterPromptLines` 带上 persona**，让大模型拿到「邓肯」而不是「Navy SEAL」—— 拿到兵种写不出有人味的对白。
5. **`nationLabelOf()` 显示到定妆表卡片**，让「同阵营同国籍、敌我不同国籍」这条约束**可被用户核对**（也正是它立刻暴露了 §48 的三处误标）。

**验证**：`tests/character-lineup.test.mjs` 整组重写，从「断言模板行为」改为「断言合并后的契约」：每个 ID 都能被注册表解析、绝不出现 `CHR-C01` 这类虚构编号、同一资产在名册与定妆表里代号与姓名必须一致、全家福 Prompt 里被引号括起来的人名必须是 `persona` 而不是 `role`。

## 51. 残余风险（红队视角，第七轮）

1. **`nationOf` 仍是关键词启发式，且现在分强弱两级**。强标记优先、弱标记看阵营，比单层正则准确，但仍然是文本匹配而非知识图谱。新增国籍时要想清楚它属于强还是弱 —— 判据是「这个词会不会同时被当作地名使用」。
2. **`TEXTURE` 里仍有 6 条 `domains: ['orbital']` 之外的共享变体是「兜底」**。原型专属步骤永远优先，因此通用池现在只在原型没有对应功能时才触达。这是有意的，但也意味着通用池的文本质量更难被用户看到、更难被回归发现。
3. **`displayNameOf` 是全站唯一口径，但它依赖 `buildRoster` 先把 `persona` 填好**。任何绕过 `buildRoster` 直接构造名册条目的地方（如测试里的手写 fixture）都会退化成用 `name` 显示。这类地方一旦进入生产路径，两套口径就会重新出现。
4. **`ARCS` 与 `TEXTURE` 是手写内容库，覆盖率靠人工枚举**（第六轮第 2 条，仍然成立）。
5. **原型识别仍是「顺序敏感 + 先命中先算」**（第六轮第 3 条，仍然成立）。`DOMAIN_RULES` 本轮也加入了同样的顺序约束（orbital 必须在 air 之前），两处都需要在新增条目时想清楚插入位置。
6. **现代敌方角色包刻意使用无国别标识的「敌方 / Adversary」命名**（第六轮第 6 条，仍然成立）。这也是 §48.1 中「敌方海军陆战队员」国籍判不出来的原因 —— 是**有意的**，不是缺陷。

# 第八轮对抗审查（6.7.2 · 创作能力：现代战争与未来战争）

本轮起点是用户的诉求：

> 「要加上让它有创作能力，这个乐高项目主要是军事题材，不仅限于历史，
> 我更要的是现代战争、未来战争这样的脚本内容。」

与第六轮一样，**先把真实成片打印出来读，再下判断**。下面每一条缺陷都附修复前的实际句子。

## 52. 第一性诊断：不是「没有现代战争资产」，是「没有现代战争原型」

用户说「要现代战争、未来战争」，最省事的做法是继续加资产。但先做了一次盘点：

- 资产库里**已经有**无人机蜂群、外骨骼、忠诚僚机、高超音速载具（6.5.0 补 131 项、6.6.0 补 194 项）。
- `story.js` 的 `ARCS` 只有 **10 个原型，且全部是历史战争的形状**：潜艇猎杀 / 舰队作战 / 制空 /
  战略打击 / 两栖登陆 / 装甲对决 / 轨道作战 / 营救撤离 / 城市突袭 / 正面交战。

于是「无人机蜂群突防压制敌方雷达」只能匹配到「制空作战」原型，
「电子战与网络战压制敌方指挥节点」只能匹配到「正面交战」原型 ——
**骨架是历史的，填进去的装备是未来的。** 读起来就是一部给旧剧本换了道具的片子。

> 结论：现代战争 / 未来战争缺的不是资产，是**节拍骨架**。继续加资产只会让「未来的装备演历史的剧本」。

**修法**：新增 6 个原型，每个配一份完整 12 拍手写骨架，并按原型单写 `reaction` 收尾：

| 原型 | `arc.id` | 目标 | 威胁 |
| --- | --- | --- | --- |
| 反无人机阵地防御 | `counter-uas` | 保住要地 | 蜂群饱和 |
| 蜂群突防 | `swarm-strike` | 打瘫雷达 | 定向能拦截 |
| 高超音速打击 | `hypersonic-strike` | 穿透反导 | 中段拦截 |
| 电磁网络压制 | `ew-cyber` | 瘫掉指挥节点 | 频谱反制 |
| 外骨骼突击 | `mech-assault` | 碾开通路 | 战斗机器人 |
| 使馆撤侨 | `embassy-evac` | 撤出平民 | 围困与人群 |

## 53. 缺陷 F1（严重，内容错误）：8/20 个题材判不出年代，静默回落「现代，中东沙漠」

修复前的实际成片（「库尔斯克坦克对决」）：

```
era=null  arc=装甲对决  domain=ground
logline: 现代，中东沙漠。必须在天亮前之内挡住敌方装甲集群……
环境: 中东沙漠绿洲
装备: M1A2 艾布拉姆斯、无人战车
```

**库里明明有 WWII 池。** 这不是「不够好」，是内容错误 ——
用户写的是 1943 年的库尔斯克，引擎拍的是当代中东。

根因：`INTENT_RULES` 只认「二战」「太平洋」这类**时代词**，不认**具体战役名**，
也不认**装备型号**。用户写「库尔斯克」时，一个时代词都没命中，`era` 就是 `null`，
下游按 `Modern` 兜底。

**修法**（两层，都写进 `eraSource` 供界面显示）：

1. **具体战役名**（`eraSource='battle'`）：库尔斯克 / 阿登 / 突出部 / 敦刻尔克 / 阿拉曼 /
   市场花园 / 卡昂 / 瑟堡 / 齐格菲 / 巴斯托涅 / 东线 / 西线 / 北非；中途岛 / 瓜岛 /
   瓜达尔卡纳尔 / 硫磺岛 / 冲绳 / 塞班 / 塔拉瓦 / 贝里琉 / 珊瑚海 / 莱特湾 / 珍珠港；
   费卢杰 / 巴格达 / 摩苏尔 / 拉马迪；柏林墙 / 铁幕 / 富尔达。
2. **装备型号反推**（`eraSource='platform'`，仅在上一层没命中时启用）：
   `b-21|f-35|忠诚僚机|高超音速|电磁炮|定向能|外骨骼|蜂群|无人战车|巡飞弹` → 现代高科技；
   `b-2|f-22|f-15|f-16|f-18|m1a2|阿帕奇|黑鹰|鱼鹰|mrap|斯特赖克|海马斯|宙斯盾|
   阿利·伯克|尼米兹|福特级|弗吉尼亚级|俄亥俄级|predator|reaper|mq-9` → 现代；
   `mig-21|su-27|f-4|f-14|m60|t-62|t-64|富尔达` → 冷战；
   `t-34|is-2|虎式|豹式|谢尔曼|喷火式|bf-109|fw-190|零式|p-51|p-47` → 二战。
   **`t-72` / `t-80` 刻意排除** —— 它们横跨冷战与海湾两个时代，靠型号推必然推错。

另新增**手动指定年代**（`eraSource='override'`）：`index.html` 加了下拉框，
`parseIntentWithOverrides(theme, { era })` 让用户显式指定的时代**优先于任何识别结果**。
界面会说明这个年代是**怎么判出来的**（识别为历史战役 / 命中时代词 / 由装备型号推断 / 手动指定）。

**验证**：`era=null` **8/20 → 3/20**。剩下 3 个（跳伞飞行员敌后营救 / 敌后渗透破坏桥梁 /
护航编队反潜警戒）是**真的没有年代信息**，按设计进入「需确认年代」提示，而不是瞎猜。

## 55. 缺陷 F3（中，物理错误）：19/20 个题材的天气都是「尘雾」，真空里也起尘雾

`{weather}` 此前只有四个来源：`snow → 风雪`、`rain → 暴雨`、`night → 夜色`、其余 → `尘雾`。

后果有两层。第一层是单调：20 个题材里 19 个是尘雾。第二层更严重 —— **物理错误**：

```
修复前  镜头沿舱体外壁缓慢滑行，核心舱检修口在尘雾里无声自转，地球的弧线压在画面下缘。
```

**真空里起不了尘雾。**

**修法**：新增 `weatherFor({ domain, intent, seed })` 与 `WEATHER_BY_DOMAIN`，让气象按战场域分化：

| 域 | 气象池 |
| --- | --- |
| orbital | 真空 / 地球反照的冷光 / 背阴面的黑暗 |
| naval | 海雾 / 低垂的云 / 涌浪激起的水汽 / 雨幕 |
| air | 云层 / 低云 / 薄云 / 逆温层 |
| strategic | 夜幕 / 低云 / 尘霾 |
| ground | 尘雾 / 扬尘 / 薄雾 / 硝烟 / 沙尘 |

`intent.weather`（雪 / 雨）与 `lightingCondition`（夜）作为覆盖层，优先于域默认值。

**验证**：氛围词 **19/20 同词 → 10 种**，单一词最高占比 3/20（雨幕×3）。

## 56. 缺陷 F4（中）：场景名词的维度错误

```
修复前  镜头贴着海面低掠，潜望深度在尘雾里被压成一条发白的线，浪从画面两侧切进来。
```

`{place}` 取自原型的 `locations`，而其中混进了**深度值**（「潜望深度」）与**零件名**
（「核心舱检修口」「对接舱」「外部桁架」）—— 它们是位置，不是**区域**，
塞进「在…里铺开 / 被压成」这类句式读不通。

**修法**（两层）：

1. 把这些 `locations` 改写成真正的区域：「潜望深度上方的水层」「核心舱与太阳翼之间的连接段」
   「对接舱外侧」「外部桁架的中段」。
2. `planner.js` 改为按镜次轮转 `story.locations[i % n]` 赋 `{place}`，
   不再让旧值从别处漏进来。

**连带修掉：logline 的移动从句。** logline 是用户最先读到的一句，由
`premise` + `{角色}{姓名}带着小队{动词}{地点}` 拼成，两个部分各有一个问题：

1. **动词按战场域取，但 naval 一个域里住着两种载具。** `ENTER_VERB` 给 naval 的词是「潜入」
   （当初为潜艇写的），于是航母题材的 logline 是

   ```
   修复前  舰长佩德罗带着小队潜入太平洋。
   ```

   **航母不会下潜。** 改为潜艇按**原型**单独取词（`ARC_ENTER_VERB['submarine-hunt'] = '潜入'`），
   水面舰艇用「驶入」。
2. **地点用的是环境名，分镜用的是区域。** logline 取 `nouns.place`（环境资产名「核潜艇控制舱」），
   分镜取 `locations` 里的区域（「跃变层下的静默区」）—— **同一部片子的简介与正文指的不是一个地方**；
   而且环境名已经在 `premise` 里出现过一次，读起来是重复。
   改为移动从句取 `locations[0]`，顺带保证 logline 与分镜正文指的是同一个地方。

修复后（26 个题材全部复核）：核潜艇 → 「潜入跃变层下的静默区」、
中途岛 → 「驶入编队外围的警戒线」、F-22 → 「飞向高空云层之上」、
库尔斯克 → 「进入开阔地边缘」、轨道 → 「进入对接舱外侧」。

## 57. 缺陷 F5（中）：收尾镜的焦点与主载具

三个独立问题叠在同一镜上：

1. **10/20 个题材的收尾回退到通用模板**（「载着归队的队员缓缓驶离」）——
   `takeSlot` 的 `strict` 把 `close` 也挡住了，于是它落到 `resumeBeats` / `BEATS` 的通用池。
2. **收尾镜的载具不是本片主载具**，而是按游标轮转抽到的某一台。
3. **收尾的物理动作与载具型号不相容**：

```
修复前  反潜护卫舰冲破海面，指挥塔舱盖打开。
```

**水面舰艇没有指挥塔。** 这是把潜艇的收尾套在了护卫舰身上。

**修法**：`strict` 不再作用于 `close`；`close` 镜的载具固定为 `vehicles[0]`（本片主载具）；
`submarine-hunt.close` 的 `focus` 从 `vehicle` 改为 `hero`，改写为
「海面破开一道白痕，指挥塔舱盖掀开，{heroCallsign}探出头…」。

## 58. 缺陷 F6（中，静默指错人）：17 处占位符与 `focus` 不匹配

`{supportCallsign}` / `{enemyCallsign}` / `{vehicle}` 渲染谁，由镜头的 `focus` 决定。
当占位符与 `focus` 对不上时**不报错、不打日志**，只是把错的人写进句子：

```
修复前  【DELTA】沃尔科夫看见【DELTA】沃尔科夫的指挥车，下令开火。
```

（`focus:'hero'` 的镜头里写了 `{enemyCallsign}`，于是渲染成了主角自己。）

```
修复前  【TANGO】伊万诺夫的装甲被打出几个洞。
```

（`focus:'clash'` 的镜头里写了 `{vehicle}`，于是**敌方的载具把敌方自己打掉了**。）

**修法**：把 `focus:'hero'` 镜头里的 `{enemyCallsign}` 全部替换为「对面的 / 对方的」，
涉及 `counter-uas / swarm-strike / ew-cyber / mech-assault / embassy-evac / armor-clash /
urban-raid / general-combat / orbital-ops` 共 12 处；`armor-clash.clash` 改写为
「{heroCallsign}的车体被打出几个洞，他借着烟幕绕到{enemyCallsign}的侧后」。

另新增**静态源码扫描测试**（直接扫 `story.js` 的骨架文本）：
`{supportCallsign}` 只能出现在 `squad` 镜、`{enemyCallsign}` 只能在 `clash/enemy` 镜、
`{vehicle}` 只能在 `vehicle` 镜。这样新增节拍时写错会**在测试里挂掉**，而不是等成片印出来才发现。

## 59. 缺陷 F7（中，一眼假）：主角职务四类错误

主角承担全部指挥类节拍（goal / plan / decision / close），职务必须配得上「在镜头前布置战术」。

**① 医疗兵占据主角位。** 26 个题材里有 3 个（中途岛航母对决 / 太平洋滩头两栖登陆 /
近地轨道卫星争夺战）的主角是「军医」：

```
修复前  军医沃克带着小队潜入诺曼底海滩。
        「下一波次放飞前的十五分钟之内打掉敌方水面编队……」
```

**修法**：`selectCast` 新增结构性不变量 `NON_LEAD_UNITS`（当前为 `Medical`）——
非指挥兵种从主角位**换到后面**（换位，不丢弃，需要时照常上场救人）。

**② `ROLE_LABELS` 的键与资产对不上。** 资产用 `Navy`（6 个角色），`ROLE_LABELS` 只写了 `Naval`
（0 个角色），两边**永远对不上** —— `personaRoleOf()` 取不到池子就退化成 `DEFAULT_ROLES`，
于是「弹道导弹核潜艇艇长」在成片里显示成「队长」。这类错不抛异常、不打日志。

**修法**：逐 unit 审计后补齐 **11 个缺失键**（`Navy` / `Navy Command` / `Advanced Special Forces` /
`Aviation / UAS` / `Counter-UAS` / `Cyber Command` / `Robotics` / `Robotic Infantry` /
`Unmanned Command` / `UAS Strike` / `Media` / `Civilian`），并新增测试
「**每个资产兵种都必须有专属职务池**」把这条契约钉死。

**③ 4 个兵种的 0 号职务不是指挥职务。** `Aviation` / `Naval Aviation` 的 0 号是「长机飞行员」、
`Engineer` 是「工兵」、`JTAC` 是「前沿引导员」—— 它们语义上是组长，但字面上不是指挥职务。
改为「飞行队长」「工兵组长」「引导组长」。

**④ 关键词判域第三次骗人。** 这是本轮最有价值的一条，因为它暴露的是一个**方法论问题**：

```
修复前  中途岛航母对决 → 主角 = 美军海军陆战队喷火兵（工兵组长）
```

一场**航母对决**里没有舰长，主角是个工兵。根因是 `domainScore` 判角色靠**名字里的关键词**，
而 `USMC Flamethrower Operator` 的名字里有「海军陆战队」，于是拿到了与舰长同分的海军域加分。

这是同一类坑的**第三次**出现：

| 次序 | 关键词 | 误判 |
| --- | --- | --- |
| 第一次（第六轮 §39） | `\bcrew\b` | 航母甲板兵被判成陆战装甲车组 |
| 第二次（第六轮 §40） | `战斗` | 「战斗工兵」与「战斗机」共享二字，飞行员被挤掉 |
| 第三次（本轮） | `marine` | 陆战队工兵在航母对决里压过舰长 |

> **启发式攒到第三个反例，就该换掉它。** 新增显式的 `UNIT_DOMAIN` 兵种→域对照表（+8 分）：
> **名字可以骗人，`unit` 字段不会。**

**验证**：26 题材主角职务扫描，非指挥职务 **3 → 0**。

## 60. 资产补充（+15，791 → 806）

## 63. 残余风险（红队视角，第八轮）

1. **`ERA_COMPATIBILITY` 是手工维护的等价类**。`WWII ⇄ Pacific`、`Modern ⇄ Modern High-Tech`、
   `Gulf War ⇄ Iraq War` 三组互借是**有意**的（历史与当代确有装备重叠），
   但新增时代时必须同步想清楚它属于哪一组，否则会退化成「没有兼容项 → 只剩自己」。
2. **`PLATFORM_ERA_HINTS` 是型号白名单，覆盖必然不全**。刻意排除了跨时代型号（T-72 / T-80），
   代价是写「T-72 集群突击」时仍会 `era=null`。这是**用召回率换准确率**的自觉取舍 ——
   推错年代（把 1980 年代拍成海湾战争）比不推年代（提示用户确认）更糟。
3. **`UNIT_DOMAIN` 与 `ROLE_LABELS` 现在都是「新增 unit 必须同步改三处」的契约**
   （资产 `unit` 字段、`ROLE_LABELS` 职务池、`UNIT_DOMAIN` 域归属）。
   已加测试守住 `ROLE_LABELS`，但 `UNIT_DOMAIN` 漏项**不会报错**，只会静默失去那 8 分。
   下一轮应补一条「每个 unit 必须在 `UNIT_DOMAIN` 里有显式取值」的测试。
4. **`ARC_ENV` 是手写表，覆盖率靠人工枚举**（与第五轮第 2 条同类）。
   新原型若忘记登记，环境会退回 `intent.setting` 或域兜底 —— 不报错，只是选得不够准。
5. **`WEATHER_BY_DOMAIN` 的池子仍然很小**（每域 3–5 个词）。
   20 题材里单一词最高占比 3/20，已经不再「一眼重复」，但同一域内连拍多部仍会撞。
6. **原型识别仍是「顺序敏感 + 先命中先算」**（第六轮第 3 条、第七轮第 5 条，仍然成立）。
   本轮新增的 6 个原型全部 `prepend` 在历史原型**之前**，因此必须复核：
   `counter-uas` 会不会抢走 `air-superiority` 的题材？已加测试「未来战争原型不得抢走历史原型」，
   但新增原型时仍需手工确认插入位置。
7. **`eraSource='platform'` 只在第一层完全没命中时才启用**。若题材同时含时代词与型号
   （「二战风格的 F-35」），以时代词为准 —— 这是有意的，但用户可能期望型号更权威。

## 64. 缺陷 G1（严重，静默失效）：39 个机位里 36 个是死代码

机位、灯光、调色此前共用同一个选取函数：

```js
const pickMany = (r, kind, intent, limit = 3) => {
  const eraMatches = all.filter(a => a.series === intent.era);
  const pool = eraMatches.length > 0 ? eraMatches : all;
  return pool.slice(0, limit);          // ← 取数组前三个
};
```

两处错叠加：

1. **`eraMatches` 是替换而不是并集。** 它只含该时代**专属**资产，却**替换**了整个池。
   二战只有 1 个时代专属机位 → 二战影片只拿到 1 个机位。时代专属资产应该是**加分项**。
2. **`slice(0, limit)` 不判域、不判时段。** 39 个机位里 **36 个是死代码**；
   实测「滩头低角度推进跟拍」跨 10 个题材被用了 **48 次**。

修复：新增 `src/domain/visual-language.js`（约 260 行），`pickMany` **整个删除**。

| 环节 | 规则 |
| --- | --- |
| 候选池 | `poolFor()` 返回**并集**：时代相容资产 ∪ 全部资产 |
| 过滤 | 域 / 时段 / 地貌三级，级联放松 `strict → todOnly → all` |
| 去重 | 全片去重，同一机位最多 3 次，优先选「没用过且得分 > 0」的 |
| 打分 | `+40` 域命中 / `+30` 戏剧功能命中 / `+themeMatch×2` 题材词命中 |

实测（7 题材 × 12 镜 = 84 镜）：**28 个不同机位被用到**，每题材 **12 个不同机位**，
无任何机位超过 3 次/片。

## 67. 缺陷 G4（严重，内容错误）：4 秒的快切里装着 8 秒的叙事

实测（修复前）：

| 时长档 | 平均字数 | 平均分句数 | 最长 |
| --- | --- | --- | --- |
| 4 秒 | **64 字** | **3.6** | 76 字 / 5 句 |
| 6 秒 | 55 字 | — | — |
| 8 秒 | 55 字 | — | — |

**最短的镜头塞了最多的内容**，时长与内容量完全脱钩。

`planner.js` 新增内容预算模型：

```js
const SPEECH_CHARS_PER_SEC = 4.5;
const VISUAL_SECONDS_PER_CLAUSE = 2;

export function contentSeconds(text) {
  const dialogues = [...text.matchAll(/「([^」]*)」/g)]
    .map(m => m[1].replace(/^【无线电】/, '').replace(/\s/g, ''));
  const speech = dialogues.reduce((s, d) => s + d.length, 0) / SPEECH_CHARS_PER_SEC;
  const visual = clauseCount(text.replace(/「[^」]*」/g, '')) * VISUAL_SECONDS_PER_CLAUSE;
  return { visual, speech, total: Math.max(visual, speech) };   // ← max，不是 sum
}
```

**两版被否掉的模型都记在代码注释里**，因为它们各自踩过坑：

1. 把对白按「分句」与画面同等计费 → 正常的两人对白被误判为「装不下」，
   **226 / 312 镜**被强行拉到 8 秒。
2. `speech + visual` **相加** → 4 秒快切全部不可能成立，**4 秒档彻底消失**
   （6s×16、8s×104）。无线电对白是**压着画面播**的，不能与画面时间相加 —— 取 `max`。

配套**改写 89 处正文**：16 组 `deadline/objective/stake` 任务简报、16 个 `contact`
各删一个冗余分句、10 个过长的 `reveal/reaction/decision/clash`、16 个 `cost` 压成硬切。

实测（26 题材 × 12 镜 = 312 镜）：**内容超时 0 个**。

## 76. 第一性诊断：三个 bug 叠出来的「节奏倒挂」

「最高潮是全片最慢的一段」不是审美问题。把编译产物按戏剧功能逐条打表之后，
三个**各自看起来都在工作**的实现叠在一起，稳定地产生同一个结果：

| # | 位置 | 错在哪 | 后果 |
| --- | --- | --- | --- |
| 1 | `planner.js` | `Number(beat.duration) \|\| 8` | 原型（`story.js` 的 `SLOTS`）里的节拍**全都不写 duration**，于是**每一条都默认 8 秒** |
| 2 | `planner.js` | `VISUAL_SECONDS_PER_CLAUSE = 2`（一律 2 秒/分句） | 「拐角。两米。」（3+2 字，纯顿挫）被算成 **4 秒**，任何快切都装不下 |
| 3 | `planner.js` | `fitDuration` 取 `max(声明, 内容)` | 内容一超，声明就被静默顶掉 |

第 1 条是主因：声明 4 秒的快切（`contact` / `clash` / `cost`）被静默升格成长镜。
第 2 条让它无路可退 —— 连「拐角。两米。X 与 Y 同时抬枪开火」都要 6 秒。
第 3 条把两者焊死。

**为什么三轮都没发现**：前几轮的诊断都在读 `action`（中文叙事正文）。
正文本身是好的 —— 每一句都通顺、都有画面。**只有把「正文需要的秒数」与
「这一镜声明的秒数」并排放到同一张表里，错位才显形。**

## 77. 缺陷 H1（严重，静默失效）：原型节拍从不声明时长，`|| 8` 把快切全部升格成长镜

`narrative.js` 的共享 `BEATS` 每条都写 `duration`；而 `story.js` 的 `SLOTS`
（16 个原型 × 13 个功能 ≈ 208 条）**一条都不写**。旧代码：

```js
duration: fitDuration(actionText, beat.duration, profile?.durations)
//            ↑ beat.duration 对原型节拍永远是 undefined
// fitDuration: Math.max(Number(undefined) || 8, need) → 至少 8 秒
```

于是**每一条原型节拍的下限是 8 秒**，而 `contact` / `clash` / `cost` 声明的是 4 秒。
声明的 4 秒从来没有机会生效。

修法：把 `FUNCTION_DURATION` 从 `const` 改为 `export`，并把它接成兜底：

```js
duration: fitDuration(actionText, beat.duration ?? FUNCTION_DURATION[beat.fn], profile?.durations)
```

## 78. 缺陷 H2（严重，模型错误）：分句时长一律 2 秒，把「顿挫」当成「画面」

`VISUAL_SECONDS_PER_CLAUSE = 2` 是一个**不分信息量**的模型。而本项目的结构骨架
大量使用短促断句制造节奏：

```
拐角。两米。X 与 Y 同时抬枪开火。
→ 3 个分句 × 2 秒 = 6 秒
```

「拐角。」「两米。」各只有两个字，是**顿挫**，不是两秒的画面。
于是所有本该是快切（声明 4 秒）的接触镜被误判成 6–8 秒。

修法：按字数加权（`0.6 + 0.09×字数`，钳在 0.8–3.0s），并**剔除 `【代号】`** ——
那是角色标识，模型在紧邻的姓名里已经拿到，不该为它预留屏幕时间。

| 字数 | 旧模型 | 新模型 |
| --- | --- | --- |
| 2–3 字 | 2.0s | **0.8s** |
| 5 字 | 2.0s | 1.1s |
| 12 字 | 2.0s | 1.7s |
| 22 字 | 2.0s | 2.6s |
| 30 字以上 | 2.0s × 分句数 | 3.0s（封顶） |

## 79. 缺陷 H3（中，响应不成比例）：1.2% 的内容超出触发 4s→6s（+50%）跳跃

修好 H1/H2 之后，`fitDuration` 仍然对任何超出都**升一档**。
实测最极端的一次是 **1.2% 的内容超出**（`est-char-2` 需要 6.07s vs 声明 6s）
触发了 **6s → 8s（+33%）**；4 秒档更严重（4.05s → 6s，**+50%**）。

两边的代价不对称，必须分清：

- **档位比内容长** → 模型在末尾多出 1–2 秒没有指令可执行，**只能自己编画面**（最严重）；
- **档位比内容短** → 模型把动作压缩着演完，**快切镜本来就该紧**。

所以「略微装不下」应当**留在原档**。引入 `FIT_TOLERANCE = 0.15`：
4s 档接受 ≤ 4.71s、6s 档 ≤ 7.06s、8s 档 ≤ 9.41s。
内容超出 50%（4 秒镜要 6 秒才装得下）时仍然老老实实升档 ——
容差只吸收**模型误差量级**的偏差，不掩盖「这一镜的内容真的放错了节奏位」。

同时把 `fitDuration` 的默认档从 **8 改成 6**：默认值应当是中位数，不是最大值。

效果：被内容真的升档的镜头从 **465 降到 206**，修完正文后进一步到 **0**。

## 80. 缺陷 H4（严重，内容错误）：`reaction` 的语法时长被抬到 6s，但可达正文只有 2.6s

**这是本轮唯一一条由上一轮我自己引入的缺陷。**

上一轮我把 `reaction` 从 4s 抬到 6s，注释里写的理由是：

> 项目里所有 `reaction` 槽位都是「镜头怼在 {heroCallsign} 的脸上 + 完全静音」，
> 按字数算只要 2.6–3.2 秒，但**留白恰恰是文字量不出来的** —— 4 秒装不下一张脸。

**这个前提是错的。** 「镜头怼在脸上」只对 `story.js` 共享池里的那几条成立，
而**它们全部不可达**：`storySteps()` 把 16 个原型池排在共享池前面，
而 16 个原型**全都自带 `reaction` 槽位**。实测编译产物：

```
beatId=res-react-1  语法=6s  编译=6s  内容=2.55s  余=3.45s
    炮塔里全是硝烟味。【OBSIDIAN】谢尔盖推开舱盖。
beatId=res-react-2  语法=6s  编译=6s  内容=2.64s  余=3.36s
    炮塔里全是硝烟味。【TANGO】伊万诺夫推开舱盖。
```

**每一条 reaction 镜都空出 3.4 秒没有指令可执行** —— 模型只能自己编画面，
正是 §79 里刚写下的「最严重」的那种失败。

修法：`reaction` 回到 **4s**（2.6 秒的正文配 4 秒的档，留 1.4 秒呼吸），
并把注释里那段错误推理**原样留在代码里当反例**：
真正需要长留白的面部特写如果将来要启用，应当**在那一条节拍上单独声明时长**，
而不是把整类 `reaction` 一起抬长。

**方法论教训**：当一个功能的实际正文与它的语法时长不符时，
**先怀疑「谁才是真正被编译的那一池」**，不要先怀疑模型。

## 81. 缺陷 H5（中，自相矛盾的 prompt）：`reaction` 的景别标签与正文打架

`shotTypeFor` 无条件把 `reaction` 映射成「**反应镜头面部特写** (Reaction Close-Up)」，
但 16 条原型 `reaction` 槽位的内容是「战后小动作」。`storySteps()` 让原型池优先，
于是**首帧生图 prompt 稳定地写成自相矛盾的两半**：

```
Framing & Pose: Reaction Close-Up, …
Action context (Chinese): 炮塔里全是硝烟味
```

让生图模型去拍一张脸，而这一镜要的是推开舱盖的中景。
**首帧构图错了，图生视频会带着这个错误构图走完整镜。**

修法：改为「战后反应中近景 (Post-Battle Reaction Medium Close-Up)」——
它对两个池都成立：原型池本来就是中近景动作，共享池的面部特写由正文第一分句
「镜头怼在…的脸上」自己交代（那一句会进首帧 prompt）。

## 82. 正文精简引入并修掉的回归：11 条 `contact` 槽位丢了交战语义

**这一节记录我自己制造的错误，因为它的成因比结果更值得记。**

正文精简完成后，8 个既有测试立刻失败，全部指向同一个既有校验器：
`shot-spec.js` 的 `FACTION_CONFLICT_INVALID` ——
**对立阵营同框时动作必须含交战语义**
（`交战|交火|开火|对抗|拦截|伏击|对峙|突袭|压制`）。

我在删冗余时**连交战动词一起删掉了**，16 个原型 `contact` 槽位里 **11 条**失去语义：

| 原型 | 改前 | 改后（丢语义） |
| --- | --- | --- |
| `counter-uas` | `…钻出来，{vocab.counterDrone}同时开火，双方在{place}上空交战。` | `…钻出来。` |
| `air-superiority` | `云层被撕开，…俯冲下来，双方立刻进入交战。` | `…俯冲下来。` |
| `urban-raid` | `…枪口已经在走廊尽头等着，双方在{place}立刻交火。` | `…枪口已经在走廊尽头。` |

12 条重写的原则是**把动词加回来、同时守住 4 秒档**（`contact` 是快切，内容上限 4.6s）。
因为 `contact` 就是「首次接触」，动词天然属于这一镜，加回来不是注水：

- 有余量时加一个分句：`…从低云下面钻出来，{vocab.counterDrone}同时开火。`
- 余量不足时**替换而非追加**：`…的武装人群把街角堵死。` → `…的武装人群堵住街角开火。`
- 长名词顶破预算时删冗余修饰：`{vocab.armorRound}` 在冷战/现代是
  「尾翼稳定脱壳穿甲弹」，于是 `第一发{vocab.armorRound}在…炸开，两车正面交战。`
  → `{vocab.armorRound}在…炸开，两车交战。`

**教训**：正文精简与语义校验是两套独立的约束，**删字之前要先知道有哪些校验器在守着这些字**。
本项目已经第四次踩「改了正文触发隐藏校验」这一类坑。

   一旦某条节拍超出容差，`tests/pacing.test.mjs` 第 3 条会立刻失败，不会静默漂移。
3. **`contentSeconds` 仍然是「字数 → 秒数」的估算**，量不出「留白」。
   §80 的修正说明：**当一个功能的实际正文池与它的语法时长不符时，
   先怀疑「谁才是真正被编译的那一池」**，不要先怀疑模型。
4. **正文精简与语义校验是两套独立约束**（§82）。本轮第二次踩到
   「改了正文触发隐藏校验器」。建议下一轮给正文改动加一道
   「改动前后都跑一遍 `validateFilmPlan`」的前置检查。
5. **`.workbuddy-ai/` 下的探针脚本不进仓库**（`probe-promotions.mjs` / `probe-beats.mjs` /
   `probe-air.mjs` / `read-film.mjs` / `patch-beat-lengths.mjs`）。
   它们承担了本轮**全部**的诊断，但仓库里只留下结论（`tests/pacing.test.mjs`）。
   下一轮若要做同类诊断需要重建探针 —— 这是有意的：探针是临时工具，不是交付物。
   代价是**诊断过程不可复现**，只有结论可回归。
6. **`reaction` 的共享池（5 条面部特写）仍然是不可达的死代码**。
   本轮没有删它们（它们是 §80 里那个错误推理的来源），只是把景别标签改成了
   对两个池都成立的中近景。若要真正启用面部特写，需要让 `storySteps()`
   在「原型池没有合适 reaction」时才回落到共享池，并给那几条**单独声明 6s**。

## 87. 缺陷 I1（严重，静默失效）：`interior` 被当成并列而非互斥，潜艇舱里出现高空俯拍航母编队

最直接的证据来自《核潜艇深海猎杀》的编译产物 —— 三条指令同时写着：

```
Scene:    nuclear submarine control room, cramped compartment packed with dials,
          periscope pedestal and a dive control panel, red battle lighting
Camera:   high aerial of a naval task force in formation, carrier at the centre
          with escorts in a screen around it, long white wakes behind each hull
Lighting: hard direct sunlight over open sea, blinding specular glints scattered
          off the swell, harsh white on painted steel
```

**潜艇指挥舱里出现了高空俯拍航母编队 + 开阔海面烈日。** 模型只会生成一团糟。

根因有三层，**每一层单独看都「在工作」**：

1. **场景判定其实是对的。** `settingsOf()` 收到的是 `settingText`
   （`name + nameZh + kw`），中文名「核潜艇控制舱」命中了 `interior` 规则，
   返回 `['interior','water']` —— 完全正确。
2. **`settingOk()` 放行了它。** 旧实现只有一句
   `return settings.some(s => asset.setting.includes(s))` ——
   场景是 `['interior','water']`，`CAM-905 编队航拍` 标的是 `['water']`，
   **相交即放行**。但 `interior` 与室外类型**不是并列关系，是互斥关系**：
   一间舱室不可能同时是开阔海面。
3. **`setting` 从不参与排序。** 它只用于 `filter`，于是「通过了过滤的」与
   「真正为这个场景设计的」同分，胜负由哈希决定 —— 潜艇舱里能用的
   `LGT-902 潜艇红色战斗照明` 与通用 `LGT-004 暴风雨光照` 打平。

第 3 层还牵出一个**数据缺口**：39 个机位里只有 **10 个**标了 `setting`，
其余 **29 个**走「未标注 = 不限」的放行分支。**只要不标注，室内场景就会拿到室外机位。**

**修复**：

- `settingOk()` 改成**两档**：场景含 `interior` → 资产必须**显式**支持 `interior`，
  否则出局（哪怕它标的是 `water`）；其余情况才用「相交即放行」。
- 新增 `settingTier()`（精确 2 / 通用 1 / 其他 0）并接入**机位 / 光照 / 调色**三处排序。
- **39 个机位全部补齐 `setting` 权威标注**（新增 29、覆盖 10）。语义约定：
  `['interior','any']` = 室内外通用（微距 / 手持 / POV / 光学视角这类与场地无关的）；
  `['interior']` = 只在封闭空间成立（座舱 POV、失重舱内漂浮）；具体类型 = 室外专用。
- **舱内灯的 `tod` 修正**（7 盏）：`LGT-902 潜艇红色战斗照明` 原本标 `tod: ['night']`，
  而潜艇在水下航行时指挥舱永远是红色战斗照明，**与外界昼夜无关** ——
  标成 `night` 导致它在 tod 过滤的第一层就被淘汰，选择器回退到通用灯。

## 88. 缺陷 I2（中，自相矛盾的 prompt）：`tod` 表达不了光质，D-Day 的阴天海滩被拍成烈日海滩

```
Lighting:   hard clear midday sunlight over open ground, short deep shadows,
            bleached highlights, heat shimmer along the horizon, no cloud cover
Color grade: cool overcast, muted palette, soft contrast, classic war-drama look
```

`no cloud cover` 与 `cool overcast` 直接打架。`tod` 只有
`day / night / dawn / dusk` —— **正午与阴天同属 `day`**，表达不了光质。

**更值得记的是诺曼底的案例**：`ENV-101 诺曼底海滩` 的正文里**明明白白写着**
`overcast sky, sea foam, smoke, gritty cinematic atmosphere`，
但光照选择器**完全不看环境描述的光质线索**，只因为
`LGT-015 开阔海面强光` 的 `domain` 是 `['naval']`（比通用阴天灯更"具体"）就选中了它 ——
**D-Day 的阴天海滩被拍成了烈日海滩**，还顺带把《拯救大兵瑞恩》
（`sky=overcast`）挤出了候选池。

**修复**：

- 新增 `skyOfText()` 从环境正文推光质；新增资产字段 `sky`
  （`sunny` / `overcast` / `any`），写进 `assets.schema.json` 成为一等字段；
  光照 40 盏、调色 5 个**全部标注**。
- `selectLightings()` 把光质放在排序最前。
- `selectColorGrade()` 的排序从**字典序改成加权求和** ——
  字典序会让维度互相"吃掉"：先比域、同域再比光质，光质就把
  **题材点名**（`kw`，如「诺曼底」「城市」）挤到了最后。
  权重：域 ×100 / 光质 **+20 · 0 · −150** / 题材点名 ×10 / 场景 ×2。
  光质是**三档**而非加分项：加分档压不住题材点名的组合拳，而
  **冲突必须重罚到能压过「域」**（某个域可能只有一两个调色候选，
  域分会把唯一候选顶上来，哪怕它的光质正好相反）。
  **宁可退到「不挑光质」的通用调色，也不能自相矛盾。**
- **次要灯必须与主灯同光质**：旧代码只校验 `hits(a.tod, tod)`，于是北非沙漠的成片里
  主灯是「沙漠正午」(sunny)，而 character / plan / decision 这些私密镜换成了
  「暴风雨光线」(overcast) —— 同一场戏的阳光在特写里突然变成阴天（实测 10 镜）。

## 89. 缺陷 I3（严重，模型错误）：首帧写死 `weapon up`，312 张里 151 张的正文毫无武器

`image-compiler.js` 的 `POSE_BY_FOCUS.hero` 写死
`'the lead minifigure in the foreground, centred, weapon up'`。
实测 312 张首帧里 **196 张**写了 `weapon up`，其中 **151 张**的正文
**完全没有武器语义** —— 受害者包括：

- `world`（环境空镜：镜头缓缓升起，村庄的矮墙后在尘雾里铺开）
- `aftermath`（公路安静了，只剩下燃烧的钢铁）
- `reaction`（靠着舱壁坐下）
- `close`（探头第一次呼吸到海风）

**严重性在于首帧是 image-to-video 的输入**：姿势错了，整镜都会带着这个错姿势走完
（「靠着舱壁坐下」的镜头如果首帧是举枪站立，Veo 会先让人站起来再坐下，或者干脆一直站着）。

**修复**：`poseFor()` 按**正文**分四档 ——
静姿（跪/坐/靠/趴/蹲）→ 位移（撤离/穿过/奔跑）→ 持械（枪/射击/瞄准/弹匣）→
手部操作（按在/画出/指着/摊开）→ 中性站姿。
`ARMED_HINT` **只收「主体手上拿着什么」的词，不收战场环境描述** ——
「迎着**火力**把舰载机放出去」「正面**压制**」形容的是战场不是这个人的手，
把它们算进持械会让航母舰桥上的舰长也被画成举枪站立（这正是第一版修完还剩 9 例的原因）。

## 90. 缺陷 I4（轻）：首帧的 `Action context` 是上一镜的连接词

`LINK_BY_PREV` 的连接词被前置到本镜正文开头，而首帧取的是第一个分句 ——
于是第 5 镜首帧写成 `Action context: 手按住地图`，而本镜是海上接触。
新增 `stripLink()` 剥掉前缀，并处理剥完后可能出现的行首逗号。

## 91. 结构性死结：`air` 域一盏灯都没有

修完 §88 之后仍有 **115 镜**冲突。统计分布后规律很清楚：
**air 域 4 个题材全部 12/12 冲突**。原因是三个事实叠在一起：

- 40 盏灯里**没有一盏的 `domain` 含 `air`**（分布：any 16 / ground 13 / naval 9 / orbital 5 / strategic 4）；
- 6 盏 `sky=sunny` 的灯**全在 ground / naval / orbital**，通用灯里一盏晴天灯都没有；
- 5 个调色里**唯一的 air 域调色是《壮志凌云》**（`sky=sunny`）。

于是空战题材**必然**落到阴天灯 + 晴天调色上。

**修复**：给 `LGT-012 开阔原野硬光` 与 `LGT-013 城市正午顶光` 补 `air` 域
（空军基地停机坪与城市上空本来就是开阔硬光），并让《壮志凌云》的 `sky` 为 `any` ——
**这不是为了迁就测试**：air 域只有它一个候选，保留 `sunny` 就等于
「只要是阴天的空战就必然自相矛盾」。它的调色特征是 clean vivid + warm skin tones
（现代空军质感），光质不是它的身份标识，身份由 `domain` 与 `kw` 承担。

## 92. 本轮我自己引入并修掉的缺陷：`rain` 命中了 `terrain`

`skyOfText()` 第一版写的是裸 `rain`。而**每一个环境资产的第一行**都是
`brick-built LEGO set at minifigure scale: terrain, buildings and props…` ——
`rain` 命中了 `terrain`，于是 **26 个题材全部被判成阴天**，
库尔斯克草原的烈日也变成了阴天。

加词边界（`\brain\b`）之后，第二个误判又露出来：费卢杰的正文是
**`harsh desert sun, dust haze`** —— 烈日 + 悬浮沙尘，是晴天。
把 `haze` 当阴天会让伊拉克城市战整片变成阴天，而《黑鹰坠落》的
`warm dusty, golden-tan cast` 恰恰就是这种暖沙尘。

最终判定顺序改为「**明确的硬光词最优先** → 阴天 → 晴天」，
并在 `tests/scene-coherence.test.mjs` 里加了一条专门的断言
（「sky 判定不得被 terrain 之类的子串骗到」）锁住这个具体事实。

**这条值得记下来**：`skyOfText` 与 `settingsOf` 都是「正则读资产正文」，
而这个项目已经**第四次**被关键词骗（前三次见 §69 的 `UNIT_DOMAIN` 注释）。
只要判定建立在正则上，这类错就会反复出现。

## 95. 残余风险（红队视角，第十一轮）

1. **这些 prompt 仍然一次都没有真正跑过 Veo 3 / Flow。**
   本轮的每一条断言都是「prompt 内部自洽」，而不是「模型会拍出这个画面」。
   `README.md` 自己写着「本地运行采用确定性规则引擎……无需外部 API 依赖」——
   所以全部 259 项测试、810 项资产、盲测 100/100/100/96%，
   验证的都是**自我一致性**。要把「自洽」升级成「有效」，
   唯一的办法是拿几条编译产物真去生成、把结果喂回来做对照。
   **这是本项目当前最大的未知，且它无法靠继续增加静态断言来消除。**
2. **`skyOfText()` / `settingsOf()` 仍是正则判定**（§92）。
   这个项目已经第四次被关键词骗。资产字段 `setting` / `sky` 现在有了权威标注，
   但**环境资产的 `setting` 仍然是推导的**（106 个环境没有 `setting` 字段）。
   下一步应当给环境资产补 `setting` 权威标注，彻底摆脱正则。
3. **调色的光质冲突靠 −150 重罚退到通用调色**（§88）——
   「伊拉克战争城市清剿」这类题材会因此拿到《兄弟连》而不是更贴切的
   《黑鹰坠落》（当灯光确实是阴天时）。**这是有意的取舍：自洽优先于贴切。**
   根治办法是扩充调色池（目前只有 5 个），让每个域在每种光质下都有候选。
4. **`interior` 互斥规则要求资产显式标注** ——
   新增机位/灯光时若忘了写 `setting`，它会走「不限」分支进入室内场景。
   `tests/scene-coherence.test.mjs` 第 2 条对此有断言（机位必须全部标注），
   但**光照的同类断言尚未加**（40 盏目前全标注，靠的是数据而非测试）。
5. **`PoseFor()` 的四档是按关键词分的**，与 §92 是同一类脆弱性。
   目前 `weapon up` 的矛盾已归零，但新增正文用词时可能漏判。
6. **`.workbuddy-ai/` 下的探针脚本不进仓库**
   （本轮新增 `probe-scene-mismatch3.mjs` / `probe-keyframe.mjs` /
   `probe-grade-light.mjs` / `patch-camera-settings.mjs` / `patch-lighting-tod.mjs` /
   `patch-sky.mjs` / `patch-air-sky.mjs` / `dump-prompt.mjs`）。
   它们承担了本轮**全部**的诊断，仓库里只留下结论。代价是**诊断过程不可复现**。
   **但本轮的资产改动是数据而非逻辑** —— 若这些 patch 脚本丢失，
   `assets.json` 里的 `setting` / `sky` 标注将无法从任何地方重建。
   这是与前几轮不同的风险：**数据改动需要把 patch 脚本本身也视为交付物**。
   （当前处置：结论写进了 `assets.json` 与 schema，且 `tests/scene-coherence.test.mjs`
   对关键事实有断言；但标注的**依据**只存在于本轮对话与脚本里。）

# 第十二轮对抗审查（6.7.6 · 字段投递）

> 用户诉求：「你再次确认，详细分析下，看下这个项目能否还有升级空间。」
> →「按你的建议全部优化。」

§96 **起点**：6.7.5 修的是「五条指令并排读」的内部自洽。本轮换查法 ——
不读指令之搭不搭配，而是**逐个字段核对「分镜设计好的东西有没有真的送出去」**。
结论是：修得掉的地方都在，但有一条此前六轮从未有人问过的维度整个掉在地上。

## §97 头号发现：`shotType` 景别从未进入视频 prompt

`compiler.js` 对 `shotType` 的**引用数为 0**。这个字段被 `image-compiler.js`、
`narrative.js`、`story.js`、`planner.js`、`lego-aligner.js`、`cinema-homage.js` 消费，
**唯独视频编译器不读**。实测 0/312 镜，仅 34% 镜头靠机位资产碰巧捎带景别词，
其余 66% 把画面构图完全交给 Veo 决定。

**这不是「少一个字段」，是设计意图的断点**：分镜层为每一镜定好了景别，
编译层把它扔了。

## §98 只加景别会制造新矛盾 —— 46/74 互斥

机位资产自身也带构图描述（`tight insert close-up on hands` /
`high aerial of a naval task force`）。74 镜两侧都可判定的镜头里
**46 镜（62%）互斥**：`环境铺陈大远景 (Establishing Extreme Wide)` 配
`CAM-609 tight insert close-up on hands working`。

所以修复必须**双向**：发射景别 + 让机位选取尊重景别。

## §99 方法论错误：把镜头焦距词当景别档

第一版 `SIZE_EN` 匹配 `wide 28mm lens` / `wide 14mm lens` —— 那是**焦距**，
不是景别；`overhead` / `top-down` / `low-angle` 是**机位角度**。据此得出
「33 镜冲突」的虚高数字。改为只认真正的构图描述后，真实冲突是 46/74。

**教训**：这一轮的全部价值建立在「判定标准是否精确」上。
一个宽松的正则会把结论从 46 镜变成 33 镜，方向都对、数量全错。

## §100 探针与实现同源，无法证伪自身

`tests/scene-coherence.test.mjs` 的持械判据正则是
`/枪|射击|开火|举枪|端枪|瞄准|弹匣|炮|扫射|刀|武器|手雷|火箭筒|交火|对射|换弹/`
—— **和源码旧实现一模一样**。所以「炮塔」命中「炮」，探针认为「有武器语义」而放行。

这是本轮最重要的元发现。已换成语义独立判据：正判据必须是「动词 + 手持物」
的完整说法，外加 7 条反向陷阱（`炮塔` / `装甲集群` / `炮兵阵地` / `机枪巢` /
`舰炮` / `第一架起飞` / `第二架起飞`）。

## §101 夹具里的第二个隐藏 bug：名册一直是空表

`compileAll()` 调 `buildRoster(r.roster, registry)`，而 `buildRoster(shots, …)`
读的是 `shot.subjects` —— **名册条目没有这个字段**。于是名册为空，
`Subject(s)` 行丢掉代号、`Cast` 行整行消失，
「代号必须出现在视频脚本里」这条保证**从未被真正测到过**。

改为 `buildRoster(r.plan.shots, registry, { leadId: r.story?.protagonist?.id })`。
修正后第 1 镜的产物才第一次完整出现：
`Subject(s): [CHR-106] 【DELTA】苏军坦克车长 / Soviet Tank Commander — …`
与 `Cast (must keep identical appearance across all shots): 【DELTA】… (CHR-106).`

## §102 景别兜底：惯例不是设计

78 镜（25%）的标签只声明运镜与氛围（`揭示推轨镜头` / `载具主导 · 压力升级跟拍` /
`残局静默收尾`）。按**戏剧功能的通行惯例**兜底，且只给 `ws` / `ms` 两档 ——
**不给 `cu`**：特写必须由分镜明说，兜底不能替导演决定拍多近。

已在 CHANGELOG 的残余风险里如实记录：这是通行惯例，但终究不是那 78 镜自己的意图。

## §103 转写而非删除

`【DELTA】` 直接删会弄丢人物归属：`Cast` 行绑定 `DELTA ↔ CHR-106`，
删掉标记后 Action 里的人物名（伊万诺夫）与 `Subject(s)` 里的资产（CHR-106）断联。
改为 `（DELTA）`：中文书名号去掉（可能被渲染成屏幕文字），圆括号保留归属。

# 第十三轮对抗审查（6.8.0 · 自主想象力）

> 用户诉求：「还是太差劲，项目里面我输入不同场景的提示词，生成的视频脚本大多数都是
> 重复的，完全没有创新能力，这样的项目怎么能够长远，需要更新为有自主想象能力，
> 能够根据用户提供的简单的描述生成多种视频脚本，但是前端页面只保留最经典，最完美，
> 内容最好的显示在前端页面。」

§105 **起点**：前十二轮修的都是「一部片子的质量」。本轮用户指出的是另一个维度 ——
**一句描述只对应一部电影**。这与前面修过的任何一条都不是同一类错误：
前面每一轮的验收单位是「这一镜对不对」，本轮的验收单位是「这句描述还能不能是别的片子」。

## §106 头号发现：重复是可以量化的，而且数字很难看

取 26 个内置题材 × 若干镜头数共 **408 镜**，把每一镜的动作句骨架化
（引号归一为 `Q`、编号归一为 `N`、标点全部剥掉），得到 **332 个不同骨架** ——
**34.6% 的镜头与其它片子共用同一个句子骨架**。

根因只有一句：`planFilm` 的 seed 是 `主题｜镜头数`，而**视角 / 叙事重心 / 基调
三个维度根本没有参数化**。它们是常量。换题材等于换名词，骨架不动。

## §107 第二个发现：场景选错，库里却有对的资产

12 条任意提示词里 **3 条明显错、4 条半错**：

| 提示词 | 选中 | 库里其实有 |
| --- | --- | --- |
| 黎明时分强渡冰河 | `ENV-001 中东沙漠` | `ENV-503 渡河点` / `ENV-306 北极冰原` |
| 月球表面争夺登月舱 | `ENV-001 中东沙漠` | `ENV-703 月面基地` |
| 侦察班穿越沼泽 | `ENV-001 中东沙漠` | `ENV-507 泛滥的沼泽地` |

三条全部落到同一个 `ENV-001`，这不是巧合，是**选型器对题材是瞎的**：
`ARC_ENV` 正则筛子集 → `themeMatch` 排序 → **取第一个**。主题词与环境名对不上时
排序**全为 0**，`sort` 退化为数组原序，而 `ENV-001` 恰好是数组第一项。

**这一类缺陷的共同形状**：每一层单独看都在「工作」，组合起来等于没做。
6.7.3 的 `pickMany` 是同一个形状（`slice(0, limit)`）。

## §108 修法一：把「取第一个」换成「六条腿加权 + 三道闸」

见 `src/domain/environment-pick.js`。三条经验值得单独记：

- **专名必须按最长公共子串算，不能切二元词。** 第一版切成二元词，
  `库尔斯克` → `库尔｜尔斯｜斯克`，**一个都匹配不上**，26 个内置题材当场劣化 10 个。
- **动作词必须剥掉。** 「伏击 / 拦截 / 争夺」是动作不是地点，
  不剥会命中 `ENV-308 中欧森林伏击地带`（+17 夺冠），真正的导弹阵地排第五。
- **具体度必须当第二排序键。** 「穿越沼泽」里 `ENV-507 泛滥的沼泽地` 与
  `ENV-610 争夺中的桥梁` **同得 17 分**；直接跳到 id 散列，沼泽片就被送到了桥上。

## §109 修法二：三个正交旋钮，且先筛后选

| 旋钮 | 改什么 | 落实 |
| --- | --- | --- |
| 视角 | 谁上场 | 主角选择 / 正反方置换 / 载具优先 |
| 重心 | 讲什么 | `EMPHASIS_ARC` 换**序**不换集合 → 不变式自动保持 |
| 基调 | 怎么拍 | 机位 / 灯光 / 调色的同分决胜 |

**关键的一处设计**：候选池放大 3 倍（上限 24），打分排序后**贪心挑选**，
与已入选方案骨架重合 > 45% 就跳过。

为什么要这样：首个版本是「生成 4 个 → 扣分 → 展示」，实测 4 个方案里有两部
**骨架重合 88%**，只能靠 `diversify()` 事后打七折。**先生成后扣分是承认自己
造出了换皮；先筛后选才是「不给换皮机会」。**

## §110 打分器必须与生成实现语义独立

6.7.6 的元发现（探针与实现同源就无法证伪自身）在本轮继续成立：
`variant-score.js` **不重跑任何选择逻辑**，只读编译产物 ——
时代自洽（看 `series` 与 `intent.era`）、光质自洽（看灯光与调色的 `sky`）、
物理自洽（地面载具是否在纯海环境，**复核产物而非生成时过滤**）、
戏剧覆盖、相邻互异、对白密度、骨架多样、切题度。

权重按「错了有多刺眼」排（时代 22 / 光质 18 / 物理 16 / 覆盖 14 / …），
**这是人为判断，不是实测分布**。若日后要调，先把 26 个题材的分项分布打出来。

## §111 本轮自己引入并修掉的三个缺陷

1. **`diversify()` 读了不存在的字段**（`c.film.shots`，实际在 `film.plan.shots`）。
   `curS` 恒为空 → `if (!curS.length) continue` → 整个去重加罚**静默跳过**。
   「4 个方案里 3 个是同一部片」一次都没被抓到过。已补专门盯它的回归测试。
2. **时代池与校验器不是同一把尺子**：`planner.js` 用 `series === era`，
   `validateShotSpec` 用 `isEraCompatible`（Modern ↔ Modern High-Tech 互通）。
   界面默认示例判为 Modern 后，唯一的 `ENV-640 现代高科技地下指挥掩体`
   **连被打分的机会都没有**（全库 44 分，时代池最好的「暴风雪山口」只有 9 分，
   凭一个「暴风」二元词过线当选）。
3. **探针自己也会骗人**：统计基调覆盖率时把 kind 写成 `'colorGrade'`
   （实际键是 `'grade'`），得出「调色基调覆盖率 0/5」的假结论。
   **探针写错比不写更危险。**

## §112 结果与边界

| 维度 | 修复前 | 修复后 |
| --- | --- | --- |
| 任意提示词场景「正确或说得通」 | 约 3 / 12 | **11 / 12** |
| 4 方案**最高**两两骨架重合 | 88% | **13% – 50%**（6 题材实测 13/50/13/25/38/38） |
| 一句描述产出的电影 | 1 | **4（可切换，前端默认只展示最优）** |
| 测试 | 262 | **274 / 274** |

**§112a 骨架判据本轮自己也收紧了一次。** 最初的 `skeletonOf` 只归一引号与编号，
于是「【PHANTOM】邓肯把照片塞回胸袋」与「【OBSIDIAN】哈里森把照片塞回胸袋」
算两个骨架 —— **只换了人名的两部片被判成「完全不同」**，
「两两重合 0%」这个漂亮数字是假的。现把 `【代号】人名` 整段归一成 `P`：
骨架要衡量的是**发生了什么**，不是**谁**。

判据收紧后，单遍贪心（按分数取、重合过高就跳过）立刻不够用：
分数最高的那部会**连带挡掉三个**与自己相似的候选，凑不满 4 部，
回退分支又把最像的那部塞了回来（斯大林格勒题材实测回到 75%）。
改为**换种子重试**：每个高分候选各当一次起点贪心铺开，
再按「最大两两重合最小、其次总分最高」选最好的一组 —— 同一题材降到 **50%**。

盲测零回归：一致性 100% / 可剪辑性 100% / 合规 100% / 稳定性 96%。

**遗留风险（如实记录）**：
- **基调仍是最弱的一维**：只做同分决胜（+6），压不过「域 + 功能 + 景别」的物理分，
  8 镜片里只改出 1 处机位差异。让它参与池内筛选会与光质 / 场景 / 时代的硬约束打架，
  本轮选择先不动。
- **候选方案不落库**：刷新后备选消失，需重新生成（约 0.4–1.0 秒）。
- **边界仍然没有变**：本轮验证的是「多部片子的**差异度**与**自洽度**」，
  这些 prompt 依旧**一次也没有跑过 Veo 3 / Flow**。
  「自洽」与「有效」之间的那道墙，第十三轮依旧没有推倒。

# 第十四轮（6.8.1）：用户把「重复」拍成了截图

## §113 头号发现：一句 `else` 把整条生成链路短路了

前十三轮我一直在**自己造场景**去测重复（换题材、换镜头数、跑盲测）。
这一轮用户直接给了截图：

> 「换了两次内容了，每次第一个脚本的内容都是『两架战术直升机在灰尘弥漫的城市街道
> 低空悬停，四根粗索降绳掷下，特战队员呈战术姿态顺绳滑降，周围街道楼顶人影攒动。』
> 这到底是什么意思，**没有使用AI吗**」

三句话，三处都指对了：

1. **那句话不是 AI 生成的** —— 它是《黑鹰坠落》第 1 镜的**手写**复刻文本
   （`cinema-homage.js` 的 `CINEMA_DATABASE`）。
2. **换多少次输入都一样** —— 因为输入根本没参与选片。
3. **「没有使用AI吗」这个疑问是合理的** —— 在那个路径上，确实没有。

定位到的原句：

```js
const match = hit.film || CINEMA_DATABASE.find(m => m.id === 'black-hawk-down'); // 通用硬派军事兜底
```

`transpileMovieToLego` 的结尾是一个**无条件兜底**：任何没命中库里 9 部影片的输入，
都被静默替换成《黑鹰坠落》。12 条任意输入实测，**10 条**落进这个兜底：

```
[黑鹰坠落]            matched=黑鹰坠落   shot1=两架战术直升机在灰尘弥漫的城市街道低空悬停…
[随便写一个没听过的名字] matched=黑鹰坠落   shot1=两架战术直升机在灰尘弥漫的城市街道低空悬停…
[现代城市巷战]         matched=黑鹰坠落   shot1=两架战术直升机在灰尘弥漫的城市街道低空悬停…
[北极冰原潜艇猎杀]      matched=黑鹰坠落   shot1=两架战术直升机在灰尘弥漫的城市街道低空悬停…
[二战诺曼底登陆]        matched=拯救大兵瑞恩 shot1=希金斯登陆艇在汹涌灰暗的海水中剧烈颠簸…
```

**最要命的是这条路径的触发条件**：`callAiBrain` 先请求 `/api/ai-brain`，
失败才走本地 —— 也就是说**纯静态离线打开、或没配云端 Key 时，这条兜底就是主路径**。
用户看到的不是「边缘情况」，是「默认行为」。

**方法论教训（第三次同源）**：前十三轮我测的是「同一题材的多个方案像不像」，
从没测过「**不同题材的输出有没有变**」。这两个是完全不同的轴 ——
6.8.0 把前者从 88% 压到 13–50%，而后者一直是 0% 变化。
**测量维度的选择本身就是一种偏见**：只测自己想得到改善的地方，
就会漏掉「压根没接通」这种更严重的问题。

## §114 顺着兜底挖出的三个同源缺陷

### §114a 题材词被当成片名

别名表里混进了大量**题材词**：

| 影片 | 混进去的题材词 |
| --- | --- |
| 现代无人战争 | `蜂群` `巡飞弹` `现代战争` `高科技战争` `电磁炮` `高超音速` `网络战` `无人机` |
| 黑鹰坠落 | `城市巷战` `索降` |
| 地心引力 | `太空站` `空间站` `失重` `宇航员` |
| 壮志凌云 | `战斗机` |
| 明日边缘 | `外骨骼` `动力机甲` |
| 边境杀手 | `暗夜突击` `夜视仪` `微光暗杀` |

于是「现代城市巷战」直接命中《黑鹰坠落》。更隐蔽的是「按题材推导视听原型」
（`inferred`）那一步：它把「蒙古骑兵草原突袭」推成《边境杀手》——
**推出来的还是固定分镜**，用户换个主题拿到的还是同一部。

匹配口径本身也是错的：`alias.includes(q)` 这个**反向**包含让『战』『无人机』
这类泛词都能命中。

### §114b 开场节拍 65% 是同一句

修完匹配之后，我以为问题解决了。实测 40 个题材，**26 个（65%）的首镜都是
「把一张被汗浸皱的照片塞回胸袋」**：

```
11×  P袋里摸出一张被汗浸皱的照片看了两秒又塞了回去
 6×  P胸袋里摸出一张被汗浸皱的照片看了两秒又塞了回去
 4×  P张被汗浸皱的照片塞回胸袋低声说QP答只是把弹匣压紧
 3×  P从胸袋里摸出一张被汗浸皱的照片看了两秒又塞了回去
 2×  P一张被汗浸皱的照片塞回胸袋低声说QP没回答只是把弹匣压紧
```

根因在 `TEXTURE.character`：8 条节拍里 **5 条是照片母题**，而域匹配只认
naval / air / orbital —— **陆战与指挥题材永远落到那 2 条通用条目，而它们两条都是照片**。

**这是同一个 bug 的第二个实例**：不是「兜底到某一部片」，而是「兜底到某一句话」。

### §114c 度量本身是坏的（最危险的一个）

上面那 5 行分布里，`P袋里摸出` / `P胸袋里摸出` / `P从胸袋里摸出` 看起来是 3 个不同骨架。
它们**是同一句话**：

```
【TANGO】米勒从胸袋里摸出一张被汗浸皱的照片…      → P袋里摸出…
【VECTOR】邓肯从胸袋里摸出一张被汗浸皱的照片…     → P袋里摸出…
【LANTERN】伊万诺夫从胸袋里摸出一张被汗浸皱的照片… → P从胸袋里摸出…
【OVERSEER】施密特从胸袋里摸出一张被汗浸皱的照片…  → P胸袋里摸出…
```

`【[^】]*】[\u4e00-\u9fa5]{2,4}` 的贪心量词按「后面还有多少汉字」吃 2–4 字：
`米勒` + `从胸` 吃 4 字，`伊万诺夫` 只能吃 4 字（人名本身就是 4 字），
`施密特` + `从` 吃 4 字 —— **人名长度不同，切点就不同**。

**这意味着 6.8.0 那句「重合率降到 13–50%」是建立在一个低估重复的度量上的。**
这不是产品 bug，是**度量 bug**；而度量 bug 比产品 bug 更危险，
因为它会让你相信一个不存在的改善。

6.7.6 的教训是「探针与实现同源就无法证伪自身」（两边共用同一套粗糙正则）。
这次的变体是「**探针的正则自己就不稳**」。两次的共性：
**度量模块必须比被测对象更保守、更可验证**，不能顺手复用一套凑合的正则。

## §116 修法：节拍池重铺 + 确定性洗牌

## §120 头号发现：报错说「未定义」，可它明明写在顶层

用户贴的第二张截图：

```
✕ 转译失败: renderVariantPicker is not defined
转译异常: renderVariantPicker is not defined

▲ ReferenceError: renderVariantPicker is not defined
    at renderCurrentProject (app.js:1353:5)
    at boot (app.js:242:2)
```

`renderVariantPicker` 在源码第 1147 行，是**顶格的函数声明**：

```js
function renderVariantPicker() {
```

顶格的 `function` 声明会被提升到作用域顶端。**它不可能 "not defined"。**
这句话本身就是最好的线索 —— 报错与源码**互相矛盾**，那说明我看错了源码。

## §121 定位方法：不要数括号，让 V8 自己回答

第一反应是数括号。我写了个括号深度扫描器，它说：

```
文件末尾括号深度 = 1 ❌ 不平衡
1147  depth=1  function renderVariantPicker() {
1344  depth=1  function renderCurrentProject() {
```

但这也说不通：如果 `renderCurrentProject` 在深度 1，`boot()`（深度 0）就调不到它，
而栈里明明写着 `at boot → at renderCurrentProject`。**扫描器和运行时互相矛盾。**

我的扫描器不认正则字面量 —— 这个文件里满是 `replace(/…/g, …)`。**它不可信。**

换一个**不依赖我自己写的任何解析逻辑**的判据：让 V8 的模块链接器回答。
给每个顶格函数追加一句 `export { 名字 }` 再解析 ——
**只有真正的模块顶层绑定才能被导出**，不是的话 V8 直接报
`Export 'X' is not defined in module`：

```
describeIntent          不是顶层 ❌
applyVariantCandidate   不是顶层 ❌
renderVariantPicker     不是顶层 ❌
renderCurrentProject    顶层 ✅
```

**这是一个可证伪的判据：如果我的假设错了，它会告诉我说错了。**

6.8.0 新增这三个函数时，我把它们插在了 `$('plan').onclick = …` **之后** ——
而那行在 `bindGlobalEvents()` 体内。**缩进骗过了我的眼睛**：
它们顶格写、看起来就是模块级的，实际是 `bindGlobalEvents` 的局部函数。

## §124 为什么五道门禁一条都没拦住

| 门禁 | 为什么放过它 |

`app.js` 在 Node 里 import 不进来（要 DOM），所以**它从来没有被真正执行过一次**。

写这段注释的时候，我以为「解析一遍」就等于「页面能跑」。

## §125 修法：纯搬移 + 两条新防线

### 纯搬移

把三个函数从 `bindGlobalEvents()` 体内移到它结束之后。为了证明「只是搬、没改」，
逐行比对**行内容的多重集**（排序后 diff）：完全一致，行数 1404 → 1404。
**搬移是最容易悄悄丢代码的操作，所以它必须有一个「没丢东西」的机械证明。**

### 防线一：静态作用域门禁（`tests/syntax.test.mjs`）

对每个「没有 export 的顶格函数声明」追加 `export { 名字 }` 再解析，
报错即证明它不是模块顶层绑定。全仓 265 个顶格声明，现在 0 个有问题。

### 防线二：动态启动冒烟（`tests/ui-boot.test.mjs`）

用最小 DOM 桩**真的把 `app.js` 跑起来**（`boot()` 是模块自启动的），
`fetch` 只读三个静态 JSON、其余接口一律 503 —— 复刻用户的离线环境。
断言：`boot()` 全程无异常 + manifest 写到了构建信息 + 复现「输入雪山坚机 → 点深度转译」不再失败。

**两条防线是互补的，不是冗余的**：静态那条能**定位到名字**（报出是哪几个函数），
动态那条能抓到静态看不出的运行期问题。一条都不该省。

### 顺手修掉一个悬空脚本

`package.json` 的 `test:smoke` 指向 `node tests/smoke.mjs`，而**那个文件不存在**。
一个指向空气的脚本不会报错、也不会有人发现 —— 现在指向真的启动冒烟。

| 4 | 两条冒烟测试各自 `import` 一次 —— **ESM 有模块缓存**，第二次是空操作，`boot()` 不重跑 | 第二条测试的 `intent` 恒为空 |
| 5 | 差点漏掉反向验证 | 是它证明了新门禁真能抓到该缺陷 |

第 1 条和第 2 条是同一个病：**我倾向于相信自己的解析逻辑。**
6.8.1 的度量 bug（`skeletonOf` 的贪心量词）也是这个病。
三次同源了 —— 第一次是「探针与实现同源」，第二次是「探针的正则自己不稳」，
这次是「**我手写的解析器本身就不合格，而它给出的答案我又看得太顺眼**」。
第 4 条则是另一类：**ESM 的模块缓存让「再 import 一次」变成空操作** ——
测试代码里的「重新初始化」在模块系统面前是幻觉。

## §129 一个知识性问题，暴露了一整类从未被检查的资产

前面十五轮，我修的都是**代码**。每一轮都有明确的失败信号：
测试变红、页面报错、生成内容重复。这些信号逼着我动。

## §131 逐行核对出的真实路由

核对的方式是直接读代码，不读文档：

## §133 `.dev.vars`：`.gitignore` 的完备性该怎么推导

顺着「本地怎么配 Key」这条线，我挖出了一个**密钥泄露面**：

`.gitignore` 里列了 `.env` / `.env.local` / `.env.*.local`，
**唯独漏了 `.dev.vars`**。

而 `.dev.vars` 正是 Cloudflare 的本地环境变量约定文件 ——
`wrangler pages dev` 官方文档明确要求你建它来放本地密钥。
也就是说：**仓库主动邀请你创建一个会被提交上去的密钥文件。**

这不是「文档没写」，这是**仓库配置本身在制造泄露**。

修法是加三行：

```
.dev.vars
.dev.vars.*
.wrangler/
```

但真正要记的是**推导方式**。我原来写 `.gitignore` 时，
是按「我知道的密钥文件名」列的（`.env` 系列）。
这是错的。正确的推导是：

> **`.gitignore` 的完备性，不能按「我知道哪些文件装密钥」来写，
> 要按「这套工具链**会**让人创建哪些装密钥的文件」来写。**

`.dev.vars` 就是后者的典型 —— 我不该"知道"它，我该**推导**出它：
既然项目用 Cloudflare Pages，既然本地开发要用 `wrangler`，
那 `wrangler` 的密钥约定文件就必然会被创建。

## §137 一个追问，和一次「不再推理」的诊断

6.8.3 我花了整整一轮，把「怎么配置 AI」写成了一份逐条对得上代码的文档。
按理说，用户拿着那份文档应该能自己解决。但他没有 —— 他说「我配了，还是用不了」。

这时候有两条路：

1. **继续读代码、继续推理**，猜他可能配错了哪里，然后写一份更详细的文档。
2. **直接测量。** 线上到底有没有 Key？发一个请求就知道。

我选了第二条。整个过程不到 5 分钟：

| 探测 | 结果 |
| --- | --- |
| `POST /api/ai-brain`（抽象题材，不命中策展库） | `engine = 本地自主想象引擎 · 离线生成（非云端 AI）`、`isAiGenerated: false`、**`latencyMs: 193`** |
| `GET /api/ai-brain?probe=1` | **405 METHOD_NOT_ALLOWED** |
| `GET /api/compose/health` | 返回 `index.html`（该路由根本不存在） |

**`latencyMs: 193` 是决定性的。** 一次外部 HTTPS 调用（DNS + TCP + TLS + 响应）
最低也要上百毫秒；而 193ms 还要装下完整的本地生成。
**这个数字说明：后台根本没有发起过任何网络请求 —— 一个 Key 都没配。**

这一轮最重要的方法论结论在这里：

> **用户说的「我配了」，和系统实际的状态，是需要分别测量的两件事。**
> 我没有去问用户「你配在哪了」，而是直接探测线上。
> **凡是能实测的，就不要靠提问去猜。**

如果我按第一条路走，我会再写一份文档、再猜一轮，然后大概率还是没解决问题 ——
因为真正的问题不是「文档不够详细」，而是**系统把失败藏起来了**。

## §138 三个「看不见」叠成一个信息黑洞

诊断出「没配 Key」之后，真正值得追的问题变成了：

**为什么用户配了（或者他以为配了）之后，界面上看不出任何异常？**

答案由三层叠加而成：

1. **前端静默回退。** `src/domain/ai-brain.js` 的 `callAiBrain` 在接口失败时
   直接走本地引擎，**不提示原因**。用户看不到任何错误。
2. **徽章无条件绿色。** `src/ui/app.js` 里这一行是**写死**的：

   ```js
   $('ai-brain-status').className = 'badge badge--ok';
   ```

   它和「是否真的用了 AI」**完全无关**。于是「本地引擎」与「云端 AI 生效」
   在界面上长得一模一样 —— 用户看到绿色，就以为一切正常。
3. **没有自检入口。** 后台的 provider 失败只写进 `console.warn`。
   用户在页面上永远看不到。而 `?probe=1` 返回 405 —— **连查都没得查**。

三层叠起来，形成一个完美的信息黑洞：

> **配了 Key 没用上 → 界面看不出异常 → 只能来问「不是配了吗」。**

这里有一个值得记下的转化：

> **错误一旦被静默吞掉，它就不再是错误，而变成了一个用户体验问题。**
> 一个「配置没生效」的技术问题，被三层静默包装成了「功能正常」的假象。
> 用户最后能做的，只剩下来问我。

## §139 修法：让失败可见

| 层 | 改动 |
| --- | --- |
| 后端 · 只读自检 | 新增 `GET /api/ai-brain?probe=1`：报告哪个 Key 配了、哪个没配。掩码只给**后四位与长度**（`••••1234（长度 56）`），**不发起任何外部调用、不消耗额度、不返回密钥本身**。不带 probe 的 GET 仍然 405（契约不放宽） |
| 后端 · 诊断随响应回传 | 所有响应体新增 `aiStatus`：`aiAvailable` / `reason`（`OK` / `NO_KEYS_CONFIGURED` / `ALL_PROVIDERS_FAILED`）/ 每个 provider 的 `configured` / `tried` / `error`（**真实 HTTP 状态码**）/ `hint` |
| 前端 · 徽章诚实 | 仅当 `isAiGenerated === true` 才是绿色；回退本地一律**黄色**，并直接写出原因。策展面板那处无条件 `badge--ok` 同样修正 |
| 文档 | `docs/AI启用时机与配置.md` 新增「零、5 秒自查」章节；README 部署章节补上**此前完全缺失**的 `GROQ_API_KEY` 一行 |

设计上有一条刻意的取舍：**自检只回答「配了没」，不主动验证 Key 是否有效。**
因为验证有效性必须真的调用一次、会消耗额度。而「配了但无效」这件事，
点一次「深度转译」就能从 `aiStatus.providers[].error` 看到真实 HTTP 状态码 ——
**用真实路径做体检，不额外花钱。**

## §140 反向验证

沿用 6.8.2 立下的纪律：**新门禁必须证明自己抓得住缺陷，而不是恒绿。**

| 把代码改回缺陷态 | 新门禁的反应 |
| --- | --- |
| 徽章改回无条件 `badge--ok` | ❌ `本地回退不得显示为成功色，实际类名："badge badge--ok"` |
| 兜底响应移除 `aiStatus` | ❌ `兜底响应缺少 aiStatus，前端将无法解释原因` |

两次都精确命中，且报错信息直接指出问题所在。

## §141 一处自我更正：写进报告的错结论比写错的代码更危险

6.8.3 我在报告和 CHANGELOG 里写下：

本轮读代码时发现**这句话是错的**。`tests/backend-ai-brain.test.mjs` 有 14 条测试，
`tests/imagination-681.test.mjs` 也在测这个端点，包含用 mock fetch 覆盖的
provider 成功 / 失败 / 内容治理分支。

真实的缺口不是「零覆盖」，而是更精确的一件事：

> 更正必须留痕，否则它就变成了另一种静默。

# 第十八轮（6.8.5）：我造的工具，第一个证伪的是我自己的诊断

> 6.8.4 我刚上线只读自检，并据此宣布：**「后台一个 Key 都没配」**。
>
> 自检上线后的第一件事，就是**推翻了我自己的这个结论**。

## §144 先更正我自己

6.8.4 我写下这样一段推断：

> 「`latencyMs: 193` 是决定性的。一次外部 HTTPS 调用（DNS + TCP + TLS + 响应）
> 最低也要上百毫秒；而 193ms 还要装下完整的本地生成。
> **这个数字说明：后台根本没有发起过任何网络请求 —— 一个 Key 都没配。**」

**这个推断是错的。**

403 / 404 这类**快速失败**的调用（DNS 已在边缘缓存、TLS 连接可能复用）
完全可以在几十毫秒内返回。两次快速失败 + 本地生成，193ms 是装得下的。

我犯的错很具体：**用一个间接信号（延迟）去代替直接测量（自检），
然后把它当成结论写进了报告和 CHANGELOG。**

而讽刺的是 —— **我为此专门建的自检接口，上线后第一件事就是证伪了它。**

## §145 用户说得对：线上实测

自检上线后立刻探测生产环境：

```json
{ "aiAvailable": true, "configuredCount": 2,
  "providers": [
    { "id": "groq",   "configured": true, "keyHint": "••••iSqX（长度 84）" },
    { "id": "gemini", "configured": true, "keyHint": "••••xvuU（长度 39）" }
  ] }
```

**用户确实配了 Key —— 两个。** 再看 `POST` 的 `aiStatus`：

```json
{ "reason": "ALL_PROVIDERS_FAILED",
  "providers": [
    { "id": "groq",   "tried": true, "error": "Groq HTTP 403" },
    { "id": "gemini", "tried": true, "error": "Gemini HTTP 404" }
  ] }
```

**两个 Key 都在，两个都失败了。**

这才是真问题 —— 而它在 6.8.4 之前**完全不可见**。
用户从第一轮就在说「我配了」，他是对的；错的是我的诊断。

## §146 两个失败，两个完全不同的根因

### ① `Gemini HTTP 404` —— 模型名早已退役（这是代码 bug）

代码里硬编码 `gemini-1.5-flash`。查 Google 官方退役表：

| 模型 | 状态 |
| --- | --- |
| `gemini-1.5-flash` | **表里连条目都没有**（早已退役） |
| `gemini-2.0-flash` / `gemini-2.0-flash-lite` | **2026-06-01 已关停** |
| `gemini-3.8-flash` / `gemini-3.5-flash-lite` | 当前可用（Google 官方推荐新项目使用） |

也就是说：**Gemini 这条路已经静默 404 了很久。**
因为失败只进 `console.warn`、徽章又无条件绿色，**没有任何人知道它坏了**。

### ② `Groq HTTP 403` —— Key 被 Groq 拒绝（这是配置问题）

我没有靠猜。我用一把**故意写错的 Key** 直接打 Groq 接口复现：

```
HTTP 403 {"error":{"message":"Forbidden"}}
```

与线上返回**完全一致**。结论：线上那把 Groq Key 是被 Groq 拒绝的
（无效 / 已撤销 / 账户受限 / 地区不支持）。

**这一条我修不了** —— 需要用户到 Groq 控制台重新生成。
代码侧能做的是**把话说清楚**，而不是让用户对着一个 403 发呆。

## §147 根子不是「写错了模型名」，而是「把模型名写死了」

值得单独记下来的一点：**模型名会腐烂。**

`gemini-1.5-flash` 当年是正确选择；它退役不是任何人的错。
真正的错误是**把模型名硬编码进函数体** —— 一次退役就永久失效，
除了改代码没有任何办法修，而且**失效是静默的**。

这构成一个永久性缺陷类别：

> **凡是「外部契约」被硬编码进代码的地方，都会在外部契约变化时静默失效。**
> 模型名是外部契约，API 版本是外部契约，第三方字段名也是。

## §148 修法：让「模型腐烂」不再是一次性致命伤

| 改动 | 说明 |
| --- | --- |
| **候选模型列表** | 每个 provider 内置一串候选，**逐个尝试**；第一个 404 就自动换下一个。实测：`gemini-3.8-flash` 404 后自动切到 `gemini-3.5-flash-lite` 并成功 |
| **环境变量覆盖** | `GROQ_MODEL` / `OPENROUTER_MODEL` / `GEMINI_MODEL`（可逗号分隔多个）。**换模型不用改代码** |
| **三个写死模型的函数 → 一个通用函数** | `callGroq` / `callOpenRouter` / `callGemini` 合并为 `callProviderModel(provider, model, …)`，URL / 请求头 / 是否 json 模式全部数据化 |
| **`advice` 字段** | 光有 `Groq HTTP 403` 用户仍不知道干什么。新增把状态码翻译成「人话 + 下一步」的映射 |
| **前端弹可操作提示** | 仅在「**配了 Key 但调用失败**」时弹 toast（写明下一步）；没配 Key 是正常状态，不打扰 |
| **自检报告候选列表** | `?probe=1` 现在同时返回每个 provider 的 `modelEnvVar` 与 `models` |

## §149 反向验证

| 把代码改回缺陷态 | 新门禁的反应 |
| --- | --- |
| 把 `gemini-1.5-flash` 加回默认候选 | ❌ `gemini-1.5-flash 早已退役，不得出现在默认候选里` |
| （同时） | ❌ `AI 诊断：单个模型退役时自动换下一个，整条路不会哑掉` |

另新增一条**静态防回归门禁**：源码里不得再出现 `'gemini-1.5-flash'` / `'gemini-2.0-flash'` 字面量。
