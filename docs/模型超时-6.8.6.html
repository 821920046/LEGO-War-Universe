把「慢」和「挂死」分开

6.8.5 把模型名修好之后，云端 AI 真的通了。然后用户看到的是：点一次「深度转译」，页面几十秒没反应。

我在 6.8.5 结尾写下的判断：

「可复现 —— 这是我引入的回归。修复前 POST 1.79s 返回；现在挂死 60s+。」

这个判断半对半错。「60s+ 没返回」是事实；「挂死」是推测。

这一轮要做的第一件事，就是把这个推测变成测量。实测结果：

POST requestedShots=1 → HTTP 200，time_total 30.69s
POST requestedShots=1（再来一次） → HTTP 200，time_total 58.99s

它不是挂死，是真的很慢。

但真正的问题在下一句：当时的代码对 fetch 一行超时都没有。
于是「慢」与「挂死」在行为上完全一样 —— 请求一直挂着，前端既不报错也不回退， 用户只能干等，看起来就是死机。

所以「它没挂死」并不能让这个 bug 消失。一个分不清「慢」和「挂死」的系统， 从用户视角看就是坏的 —— 这正是 6.8.4「让失败可见」没做完的另一半。

一、根因：一行超时都没有

functions/api/ai-brain.js · 6.8.6 之前
const res = await fetch(provider.url, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json', 'Authorization': `Bearer ${apiKey}` },
  body: JSON.stringify(body)
});
// ← 没有 signal、没有 timeout、没有上限。
//   上游不返回，这个 await 就永远不返回。

两层上限 + 逐次耗时，缺一不可：

① 单次调用无超时

一次上游卡死就能吃掉整次请求的全部时间，且没有痕迹。

② 整次请求无预算

3 个候选模型 × 无上限 = 总时长不可预测，用户不知道要等多久。

③ 逐次耗时读不出来

attemptedModels 只记名字，试完只留最后一条 error，「哪个模型慢」只能靠猜。

二、顺带量到一个此前根本量不到的东西

第二次实测拿到 engine = Cloud Free AI (Gemini (gemini-3.5-flash-lite))， 而上一轮实测是 Gemini (gemini-2.5-flash) —— 两次成功的模型不一样。 这说明候选列表里第 1 个 gemini-3.8-flash 一直失败、第 2/3 个间歇成功。

先核实这两个名字是不是真的（上一轮是从搜索结果里抄的，属于二手事实）： Firebase AI Logic 官方文档列出 gemini-3.8-flash，Google Cloud 模型页列出 Gemini 3.5 Flash-Lite。两个名字都是真的 —— 所以第 1 个候选的失败 不是「名字写错了」，而是间歇性失败（额度 / 限流 / 上游过载）。

6.8.5 能给出的全部信息 —— 回答不了「为什么」
{ "attemptedModels": ["gemini-3.8-flash", "gemini-3.5-flash-lite", "gemini-2.5-flash"],
  "error": "…只有最后一条失败的原因…" }
// 三个模型试完，中间发生了什么完全丢失。
6.8.6 · aiStatus.providers[].calls —— 逐次调用记录
"calls": [
  { "model": "gemini-3.8-flash",      "ok": false, "ms": 812,   "error": "Gemini HTTP 429",
    "timedOut": false, "skipped": false },
  { "model": "gemini-3.5-flash-lite", "ok": true,  "ms": 57341, "error": null,
    "timedOut": false, "skipped": false },
  { "model": "gemini-2.5-flash",      "ok": false, "ms": 0,     "error": "跳过：整次请求总预算已耗尽",
    "timedOut": false, "skipped": true }
]

ms = 这一次真实花了多久；timedOut = 是不是超时（与 404/403 区分开）； skipped = 因为总预算耗尽没有尝试（而不是试了没成）。 有了它，「哪个模型慢、哪个模型挂」第一次变成能直接读出来的数字， 而不是靠总耗时去反推 —— 而反推正是 6.8.4 出错的原因。

三、修法

层面做法默认值 / 可覆盖
单次调用 withTimeout() + AbortController.abort()；响应头与响应体分别计时 60s · AI_PROVIDER_TIMEOUT_MS
整次请求 每次调用前判 deadline - Date.now()；单次超时再被剩余预算夹一次 120s · AI_REQUEST_BUDGET_MS
前端等待 fetch 加超时 + 每 5 秒刷新「已等待 N 秒」心跳 100s
失败归因 FRONTEND_TIMEOUT / FRONTEND_UNREACHABLE / BACKEND_ERROR（含状态码）/ BACKEND_EMPTY_RESULT 徽章如实翻译，不再一律「未使用云端 AI」

默认值刻意给得比实测宽松（单次 60s / 总计 120s）：先把「无界」变成「有界」、 并测出真实耗时分布，再依据数据收紧。实测单镜就要 30–59 秒， 如果我拍脑袋写 12 秒，AI 会重新变成「永远用不上」 —— 修一个 bug 不能顺手制造一个更大的。

四、反向验证：四条门禁，四个都真的会红

反向改动结果
① 后端超时不再触发（guard 永不 reject）✅ 红 —— 用例 13 超时挂死
② 后端去掉总预算（remaining = Infinity）✅ 红 —— 只有「总预算耗尽后必须停止尝试」失败
③ 后端不记逐次耗时（ms = null）✅ 红 —— 「单次超时」与「逐模型耗时」两条失败
④ 前端超时不再触发✅ 红 —— 进程因超时挂死

边界：① 跑出来是 # fail 0 / # cancelled 8 —— node 的 --test-timeout 把超时用例记为 cancelled 而非 failed，并取消同文件剩余用例。 所以 ① 只能证明用例 13 抓到了它，后面 8 条是级联取消，不算独立证据。②③ 是干净的定向证据。

五、我这一轮最该记下来的错误：反向验证工具自己是个假绿

第一版反向验证脚本用 child_process.execFileSync 跑子进程。它输出了：

它打印的
反向验证通过：每一条新门禁都确实能抓住它对应的缺陷。
而真相是
code=EBUSY signal=null  msg=spawnSync ...\node.exe EBUSY
real 0m0.578s

子进程一次都没起来，一条测试都没跑，0.578 秒就「通过」了。 spawnSync 抛了 EBUSY，而我的 catch 把「任何非零结果」都当成了「门禁红了」。 于是这个工具完美地复现了它要防的那类 bug： 把「什么都没发生」报告成「一切正常」。

重建 · ①

不再从 node 里 spawn node（沙箱下会 EBUSY），改为外层 bash 驱动 + cp/mv 还原。

重建 · ②

打补丁用独立工具，未命中就以退出码 2 明确失败 —— 不允许「悄悄什么也没改」也算通过。

重建 · ③

用 --test-timeout 把挂死变成有界的失败，并打印失败用例名与 code=/signal=/status=。

遗留风险（如实记录）

  • 单镜 30–59 秒仍然太慢，本轮没有解决。只做到「把无界变有界、把慢变成可测量」。 根因很可能是 system prompt 极大（导演指令 + 资产目录 + 固定阵容）每次尝试都要重传， 加上第 1 个候选白跑一次。收紧超时与精简 prompt 留给下一轮 —— 因为现在终于有 calls[].ms 可以依据了。
  • gemini-3.8-flash 为什么一直失败尚无定论。候选列表让它退化成「换下一个」， 但没诊断出是 429 / 上游过载 / 免费档配额中的哪一种。
  • 默认超时 60s / 120s 是暂定值，依据只有两次线上实测，样本太少。
  • Groq 那把 Key 仍被 Groq 拒绝（403），只能由用户到控制台重新生成，代码侧修不了。
  • 候选模型名将来同样会腐烂，只是代价从「永久哑掉」降为「换下一个」；定时真调用的健康检查仍未做。
  • 06_Deploy/worker.js 仍只支持 gemini/openai 且前端调不到它。
  • public/build-manifest.json 的 builtAt 时间戳仍会让工作区变脏。
  • 边界仍然没有变：这些 prompt 依旧一次也没有跑过 Veo 3 / Flow。
