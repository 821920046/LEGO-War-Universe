节奏：让节拍正文配得上它的戏剧节奏

用户诉求：「内容方面还是需要优化，还是不够完美，请继续在脚本内容上下功夫，让这些脚本生成的视频内容更加完美。」→「继续按你的建议优化。」

上一轮我在报告里自己写下了这条残余风险：「节奏仍然轻微倒挂 —— climax 7.92s > build 7.56s > establish 7.49s > resolve 6.79s。本轮选择不去靠删内容来追这个数字，下一轮应从 narrative.js 的结构节拍时长分配入手。」这一轮就是去还这笔债 —— 而且全程没有靠删内容。资产 810 项零改动，构建签名 2a778c168cbc 不变，测试 246 → 253。

一、根因：三个各自看起来都在工作的实现叠在一起

① Number(beat.duration) || 8

原型（story.js 的 SLOTS）里的节拍全都不写 duration，于是每一条都默认 8 秒。声明 4 秒的快切（contact / clash / cost）被静默升格成长镜。

② 分句时长一律 2 秒

「拐角。两米。」（3+2 字，纯顿挫）被算成 4 秒。于是任何快切都装不下 —— 连最典型的接触镜都要 6 秒。

③ fitDuration 取 max(声明, 内容)

内容一超，声明就被静默顶掉。前两条产生错位，这一条把错位焊死。

④ 为什么三轮都没发现

前几轮的诊断都在读 action（中文叙事正文）。正文本身是好的 —— 每一句都通顺、都有画面。只有把「正文需要的秒数」与「这一镜声明的秒数」并排放到同一张表里，错位才显形。

// 原型节拍不写 duration → Number(undefined) || 8

// 4.05s 的内容 → 4s 档装不下 → 直接跳 6s（+50%）
修复后 · planner.js
// 按字数加权，钳在 0.8–3.0s，并剔除【代号】
const CLAUSE_SEC_BASE = 0.6, CLAUSE_SEC_PER_CHAR = 0.09;
const CLAUSE_SEC_MIN = 0.8,  CLAUSE_SEC_MAX = 3.0;
export function clauseSeconds(clause) {
  const chars = String(clause ?? '')
    .replace(/【[^】]*】/g, '').replace(/\s/g, '').length;
  if (chars === 0) return 0;
  return Math.min(CLAUSE_SEC_MAX,
    Math.max(CLAUSE_SEC_MIN,
      CLAUSE_SEC_BASE + chars * CLAUSE_SEC_PER_CHAR));
}

// 节拍自己声明优先，否则回落到戏剧功能的语法时长
// 默认档 8 → 6：默认值应当是中位数，不是最大值
// 15% 容差：1.2% 的超出不该触发 +50% 的跳跃
duration: fitDuration(
  actionText,
  beat.duration ?? FUNCTION_DURATION[beat.fn],
  profile?.durations
)

分句时长：从「一律 2 秒」到「按信息量加权」

字数旧模型新模型说明
2–3 字2.0s0.8s顿挫 / 强调，不是两秒的画面
5 字2.0s1.1s
12 字2.0s1.7s一个完整动作
22 字2.0s2.6s铺陈描述
30 字以上2.0s × 分句数3.0s（封顶）再长就该拆成两个镜头

统计字数时剔除 【代号】 —— 那是角色标识，模型在紧邻的姓名里已经拿到，不该为它预留屏幕时间（否则「【CROSSBOW】T-34/85 中型坦克…」会凭空多出 0.6 秒）。

四、精简过程中踩到的既有校验器（记录我自己的错误）

正文精简完成后，8 个既有测试立刻失败，全部指向同一个校验器：shot-spec.js 的 FACTION_CONFLICT_INVALID —— 对立阵营同框时动作必须含交战语义（交战|交火|开火|对抗|拦截|伏击|对峙|突袭|压制）。我在删冗余时连交战动词一起删掉了，16 个原型 contact 槽位里有 11 条失去语义：

修复前 · 11 条 contact 槽位丢了交战语义
[counter-uas]      {link}第一波蜂群从低云下面钻出来。
[swarm-strike]     {link}{enemyCallsign}的防空火力把天空切成一块块。
[air-superiority]  {link}{enemyCallsign}的双机编队从太阳方向俯冲下来。
[urban-raid]       {link}门被踹开的瞬间，{enemyCallsign}的枪口已经在走廊尽头。
[general-combat]   {link}刚越过出发线，{enemyCallsign}的火力就压了过来。

12 条重写的原则是把动词加回来、同时守住 4 秒档（contact 是快切，内容上限 4.6s）。因为 contact 就是「首次接触」，动词天然属于这一镜，加回来不是注水：

加回来 · 有余量时加一个分句
{link}第一波蜂群从低云下面钻出来，{vocab.counterDrone}同时开火。
→ 内容 2.82s → 4.23s（仍在 4 秒档）
加回来 · 余量不足时替换而非追加
{enemyCallsign}的武装人群把街角堵死。（3.96s）
{enemyCallsign}的武装人群堵住街角开火。（4.05s）

长名词会顶破预算：{vocab.armorRound} 在冷战 / 现代是「尾翼稳定脱壳穿甲弹」， 于是删掉冗余的「第一发」——第一发{vocab.armorRound}在…炸开，两车正面交战。 → {vocab.armorRound}在…炸开，两车交战。。 复测：16/16 条 contact 槽位全部含交战语义，且全部落进 4 秒档。

五、自我纠错：reaction 的语法时长从 6s 回到 4s

上一轮我写下的错误推理（原样保留在代码注释里当反例）
项目里所有 reaction 槽位都是「镜头怼在 {heroCallsign} 的脸上 + 完全静音」，
按字数算只要 2.6–3.2 秒，但留白恰恰是文字量不出来的 —— 4 秒装不下一张脸。
→ 于是 reaction 从 4s 抬到 6s

这个前提是错的。「镜头怼在脸上」只对 story.js 共享池里的那几条成立， 而它们全部不可达 —— storySteps() 把 16 个原型池排在共享池前面， 而 16 个原型全都自带 reaction 槽位。实测编译产物：

修复前 · 每一条 reaction 镜都空出 3.4 秒没有指令可执行
beatId=res-react-1  语法=6s  编译=6s  内容=2.55s  余=3.45s
    炮塔里全是硝烟味。【OBSIDIAN】谢尔盖推开舱盖。
beatId=res-react-2  语法=6s  编译=6s  内容=2.64s  余=3.36s
    炮塔里全是硝烟味。【TANGO】伊万诺夫推开舱盖。

模型只能自己编 3.4 秒画面 —— 正是 FIT_TOLERANCE 注释里写的「最严重」那种失败。

reaction 回到 4s：2.6 秒的正文配 4 秒的档，留 1.4 秒呼吸。 真正需要长留白的面部特写如果将来要启用，应当在那一条节拍上单独声明时长， 而不是把整类 reaction 一起抬长。

方法论教训：当一个功能的实际正文池与它的语法时长不符时， 先怀疑「谁才是真正被编译的那一池」，不要先怀疑模型。

同时修掉一处自相矛盾的 prompt

shotTypeFor 无条件把 reaction 映射成「反应镜头面部特写」， 但 16 条原型 reaction 槽位的内容是「战后小动作」。首帧生图 prompt 于是稳定地写成：

修复前 · 首帧构图与正文打架
Framing & Pose: Reaction Close-Up, …
Action context (Chinese): 炮塔里全是硝烟味
修复后 · 对两个池都成立
Framing & Pose: Post-Battle Reaction
Medium Close-Up, …
Action context (Chinese): 炮塔里全是硝烟味

让生图模型去拍一张脸，而这一镜要的是推开舱盖的中景 —— 首帧构图错了，图生视频会带着这个错误构图走完整镜。

八、新增测试（+6）

tests/pacing.test.mjs —— 断言全部基于真实编译产物（planFilm 的输出），不是内部字段：

① 语法表完整合法

FUNCTION_DURATION 必须覆盖所有用到的戏剧功能，且只落在模型支持的档位 [4,6,8] 上。

② 覆盖必须逐条登记

BEATS 里对语法表的覆盖必须与 JUSTIFIED_OVERRIDES 完全一致（含「陈旧条目要删掉」）。

③ 回归靶心

没有任何镜头的内容把它的声明时长顶到更高一档（样本 > 500 镜）。

④ 容差不能掩盖错位

内容超出声明时只能落在容差带内，超出即失败。

⑤ 曲线必须有起伏

铺陈最慢、高潮最快、落差 ≥ 1.0s。

⑥ 快切不许空转

4 秒档必须真的被用到（≥ 10%），且正文至少占满一半时长。

另把 tests/visual-language.test.mjs 的时长断言从「内容 ≤ 时长」放宽到「内容 ≤ 时长 ×(1+容差)」，并把这条设计变更的理由写进了测试注释；同时把「不得超过模型单镜上限」拆成独立一条硬约束（8s ×(1+容差)）。

九、残余风险（如实记录）

  1. climax 与 resolve 只差 0.01s（5.40 vs 5.41）。形状是对的（铺陈最慢 → 加速 → 高潮最快 → 结尾回落），但「回落」这一笔目前只靠 aftermath / close 两个 6–8 秒档撑住。若要更明显的呼吸感，下一轮可考虑给 resolve 增加一个 8 秒档节拍，而不是继续拉长正文。
  2. observe / plan 类节拍仍有 0.27–0.44s 的轻微超出，落在 15% 容差带内。这是有意接受的：再删就要删到语义。但容差不是无限的 —— 一旦某条节拍超出容差，第 3 条测试会立刻失败，不会静默漂移。
  3. contentSeconds 仍然是「字数 → 秒数」的估算，量不出「留白」。第五节说明：当一个功能的实际正文池与它的语法时长不符时，先怀疑「谁才是真正被编译的那一池」，不要先怀疑模型。
  4. 正文精简与语义校验是两套独立约束（第四节）。本轮第二次踩到「改了正文触发隐藏校验器」。建议下一轮给正文改动加一道「改动前后都跑一遍 validateFilmPlan」的前置检查。
  5. .workbuddy-ai/ 下的探针脚本不进仓库（probe-promotions.mjs / probe-beats.mjs / probe-air.mjs / read-film.mjs / patch-beat-lengths.mjs）。它们承担了本轮全部的诊断，但仓库里只留下结论。代价是诊断过程不可复现，只有结论可回归。
  6. reaction 的共享池（5 条面部特写）仍然是不可达的死代码。本轮没有删它们（它们是第五节那个错误推理的来源），只是把景别标签改成了对两个池都成立的中近景。若要真正启用面部特写，需要让 storySteps() 在「原型池没有合适 reaction」时才回落到共享池，并给那几条单独声明 6s。
